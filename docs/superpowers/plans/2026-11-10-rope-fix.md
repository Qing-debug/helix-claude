# Rope fix: always blink down when in reach, mark ropes in the map editor, and get off a rope: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Hong's 10-lap walks end `off_map` on Fossil Foundry 2 (FF2) because a drop launched from node 7 (105, 42) grabs the rope that hangs under it at minimap column 107, and the planner keeps choosing a drop by coin flip. After this plan: the planner never drops where a teleport down reaches (DBG146-D1); each map can have its ropes marked in the map editor, which suggests them from the minimap and refuses nodes near the places where a rope meets a platform (Hong, 2026-11-11; OUTLINE147-E1); and the walker uses the marks to know at once that the character hangs on a rope and gets it off (blink to the nearer platform in reach, else Alt+Left/Right; DBG146-D2, OUTLINE147-E2). ## Choices this plan makes (not Hong's words)

- **C1, the rope zone** (where a still off-graph read counts as "on this rope"): x within `rope_zone_half_px` (2) of the rope's read x (`column + ON_ROPE_DX`, `ON_ROPE_DX = -1`), and y with `top_y < y <= bottom_y`, in map coordinates. Measured zone (OUTLINE147): column-2 .. column, top-6 .. bottom+1 for the visible part; widened by 1 px each side in x for a minimap cropped 1 px differently (OUTLINE147's [review] on the crop; decisions.md H85 "Limits"). Widening is safe here because only reads the map cannot place and that hold still are checked (Review Focus 1, 3): on FF2 the only such reads at those columns in 13 saved runs are the rope reads (OUTLINE147 3.2). No crop-offset check at map load is built (OUTLINE147 named it for a 1 px outline; with node lines and this margin it is not needed now; open item in the change log).
- **C2, how often**: at one rope the rule sends at most `rope_blink_tries` (2) blinks, if a blink is in reach, then one jump off, then ends the run `off_map`. A blink can be a no-op (live and in sim), hence two; Hong's order (blink, else jump off, `off_map` last) is kept.
- **C3, which way to jump off**: toward the leg target's x; right when it is level with the read.
- **C4, the `abilities` sim check** (ruling ROPE146-D2 = A, stands): it needs teleports down > 0, and drops > 0 only when the route graph has a DOWN edge with `dy > reach_v` (a drop-only edge; none on FF2). Counting over every DOWN edge rather than the ones `_offered` keeps is deliberate: a drop-only edge no path uses makes the check fail, never pass falsely (ROPE146R m-4). After H87 no FF2 sim run exercises the walker's drop path; unit tests cover it (Task 1).
- **C5, the simulated rope grab**: a drop launched within `rope_grab_px` (2) of a rope's read x, from the platform the rope hangs from, grabs it (what DBG146 saw live). Because FF2 no longer drops after H87, the simulator also has `NoiseConfig.rope_grab_p` (default 0, no draw at 0): a teleport down launched under the same condition grabs the rope with that chance. That is a test device, not a live observation (DBG146 saw teleports down from node 7 work). The grab depth is drawn from `rope_grab_depth_px` (3, 9) below the rope's top, so some grabs land where `attach` places the read on the platform above and some off-graph; no test pins which regime a given grab is in (ROPE146R m-2).
- **C6, the new move's names**: `MoveKind.JUMP_OFF = "jump_off"`, `actions.jump_off`, `InputLayer.jump_off(direction, stimulus_ns)`; the plan name in the `ActionRecord` is `"jump_off"`; the route view shows "jump off left" and "Left+Alt".
- **C7, the DOWN edge's cost** follows H87: `route_graph._edge_cost` prices a DOWN edge at the teleport's cost when a teleport reaches, else the drop's (today it takes the cheaper of the two, which for a drop of under 12 px would price a move H87 never makes). No FF2 edge changes cost (its DOWN edges are 17 and 18 px, where the teleport is already cheaper: drop 0.63-0.65 s > teleport 0.55 s). On another map a DOWN edge of under about 12 px now costs and plays a teleport (0.55 s) where the drop (0.35 s + dy/60) was cheaper: a slightly slower short down move there. That is H87's own effect (Hong's pick), not a choice of this plan (ROPE148R m-5).
- **C8, the rope file**: `<map stem>.ropes.json` beside the map CSV (`maps/fossil_foundry_2.csv` → `maps/fossil_foundry_2.ropes.json`), UTF-8 JSON: `{"format": "helix-ropes", "version": 1, "minimap_size": [w, h], "ropes": [{"x": 107, "top_y": 43, "bottom_y": 61}, ...]}`. `x` is the rope's minimap column as drawn; `top_y` and `bottom_y` are the map-coordinate y of the platform it hangs from and of the platform it reaches (where a node on that platform would sit). Readers ignore top-level keys they do not know and the editor writes them back unchanged, so a later `"platforms"` outline can be added without a new version. Modules: `src/controller/rope_file.py` (format, reader, writer, keep-out test) and `src/controller/rope_finder.py` (the finder), pure and Tk-free, because the editor, the walker's session and the simulator all read the file and `src/controller` is the one package all three may import.
- **C9, how still is "on the rope"**: a read in a rope zone gets its move once it has been read the same for `rope_still_s` (0.1 s, two polls after the first; the walker's settle already needed two equal reads). A fall is at least 3 px per 50 ms poll at the planner's 60 px/s, so a falling read does not hold for 0.1 s; H85's 0.5 s stays for every other off-graph read. Saves about 0.4 s per rope event against H85's wait (OUTLINE147 3.3 measured 0.58 s per drop-settle-wait cycle on the rope).
- **C10, a rope read the map places: a known limit, not handled** (ROPE148R I-1). A read on a rope within 3 px of a platform line (e.g. (106, 44) and (106, 45) on rope 107; the one rope-46 grab read seen live, (46, 30), 2 px under the top line 28) is placed by `attach` (A2) and planned as a platform read, so the rope rule never sees it (`walker.py:224-227`). After H91 every node is at least 6 px from a rope's read x, so the walker stands at least 4 px from it (`arrive_px` 2) and the first move planned from such a read is a walk: lining up on the node's x before UP/DOWN (P4, `planner.py:225-231`, kept by H89) or a walk along the platform. A walk on a rope does nothing (in the sim `walk` is `none` on a rope, Task 5; live: inferred, not observed). The read stays placed, so the leg repeats the no-op walk until `leg_timeout_s` (60 s, `walker.py:203-205`, `session.py:83`) and ends `timed_out`. A timed-out leg that sent moves does not end the run (`walker.py:64` `_ENDS_THE_RUN`; `session.py:187`), so `run` counts the leg and starts the next one (`walker.py:364-376`) with the character still on the rope: the grab repeats on every following leg, 60 s each, until something moves the character off (a knockback) or Hong presses F12, with no `off_map` and no stuck key. A 10-lap walk could so run on for up to legs × 10 × 60 s and still end `max_laps`, exit 0, so the live verifier's check (1) passes; only checks (5) (time per lap) and (6) (no `timed_out` leg) catch it. Not expected on FF2: every grab seen live was a drop (11 of 11 on rope 107, one on rope 46), H87 removes FF2's drops, and every launch is at least 4 px from a rope's read x. Ruling [standing fact] (orchestrator, 2026-11-11, orch 148: "Fix real problems, not ones we don't know will happen"): no code for it before the sign-off walk (the reviewer's optional "two no-op walks on a rope, then the rope rule" switch is not built); the live verifier's checks (5) and (6) show it if it happens, and the fix is then a small walker task. Task 8 states the limit.
- **C11, a bad rope file** is refused where a bad map is refused: the walk does not start, and the message names the file, each bad rope and how to fix it ("open the map in the map editor, mark its ropes again (Find ropes or Add rope) and save; the save replaces this file"), in line with the standing fact "Bad map files must be obvious, with how to fix them". The map editor is the exception (ruling ROPE148R-D1 = A, orchestrator, 2026-11-11, notes ROPE148A; it amends H94): it opens such a map with its nodes and no ropes, shows the reader's message plus `The map's nodes were loaded without its ropes. Mark the ropes again and save to replace the file.`, and replaces the bad file only by a save with at least one rope marked; a save with no rope marked writes the CSV and leaves the bad file as it was, so the walk keeps refusing until the ropes are marked again (Task 3a). The runtime does not refuse a map whose nodes are near a rope (that is the editor's rule; the sim fixture keeps Hong's current node 7 on purpose, to prove recovery).
- **C12, the finder rule** (OUTLINE147's rule made relative to the palette): on the per-pixel median of the collected frames, a column pixel is "rope" when its blue is at least 10 below the blue of both horizontal neighbours and both neighbours are background (grey < 120); a rope is a run of at least 6 such rows in one column. Its top is found by walking up from the run to the first row whose neighbours are bright (grey ≥ 180, a platform), its bottom by walking down to the first such row; `top_y`/`bottom_y` are those rows minus `NODE_ABOVE_GROUND_PX` (3). A run with no platform above or below is not a rope. Columns within 2 px of each other are one rope.
