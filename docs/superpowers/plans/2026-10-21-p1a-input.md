> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development`. One fresh implementer
> per task, in order. Each task is TDD (`superpowers:test-driven-development`): write the listed tests first, watch
> them fail, then implement. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the PC presses, holds and releases the bot's keys (arrows, `E`, `Alt`, `Space`, chords, holds) through the
ESP32-S3 "Guiness" acting as a real BLE HID keyboard, with human-like timing chosen on the PC, every failure visible
to the caller, and every reliability target in spec A met on real hardware.

**Architecture:** the PC samples every timing value (seeded RNG) and sends one *action* as a timed schedule of key
states over the custom GATT command characteristic. The firmware's `onWrite` only enqueues. `loop()` dequeues, plays
the schedule with `esp_timer` µs timing, and sends each HID report through the non-coalescing
`notify(value, len, connHandle)` path. It acks over the notify characteristic. A PC-side low-level keyboard hook
records what Windows actually receives; a soak harness logs both the chosen and the measured values, and an
analysis step checks each target.

ESP32 NIMBLE Keyboard 2.0.1 (author T-vK, maintainer J. van den Berg, github.com/Berg0162/ESP32-NIMBLE-Keyboard; installed
`library.properties`).

## Contracts fixed by this plan (the interfaces every task builds against)

### C1. Wire protocol v1 *(PA-D1 → A, binary v1; decisions.md PA-D1)* — **interface**

Little-endian. Board ⇄ PC over the existing custom service `a723b49a-2b53-46a6-a2db-02bb9e9a577c` (spec:L38).

**Commands**, PC → board, *write with response* (`response=True`) to `61adcd67-20e9-4c38-b1d0-879445c5b732`:

| Off | Size | Field |
|---|---|---|
| 0 | 1 | `ver` = `0x01` |
| 1 | 1 | `op`: `0x01` PLAY (queued) · `0x02` RELEASE_ALL (abort + all-up) · `0x03` PING (answered at once from `onWrite`) |
| 2 | 2 | `seq` u16, PC-assigned, increments, wraps |
| 4 | 1 | PLAY only: `n` steps, 1..16 |
| 5 | 3·n | PLAY only: per step `delta` u16 (100 µs units, from the previous step; step 0 from schedule start) + `mask` u8 |

`mask` bits: `0` LEFT · `1` RIGHT · `2` UP · `3` DOWN · `4` E · `5` ALT · `6` SPACE · `7` must be 0.

PLAY is valid only if all of these hold (checked on **both** sides; the board rejects, the PC never sends):
length is exactly `5 + 3n`; `1 ≤ n ≤ 16`; bit 7 clear in every mask; **each step changes exactly one key** relative to
the previous state (the state before step 0 is all-up), so every report is exactly one Windows key transition and
the order is unambiguous; the **last mask is 0** (closed schedule, PA-D5 → A); `Σ delta ≤ 100 000`
(10 s). On the PC only, also: **every step's `delta` ≤ 65 535** (6.5535 s, PA-adj1-D2 → A). A u16 field cannot carry
more, so the board never sees a violation. `validate_schedule` / `encode_play` return a `Failure` naming the
"per-step delta" rule and never let `struct.pack` raise. A walk is two steps, so the longest walk is 6.5535 s.
Longer walks are chained.

Closed schedules (PA-D5 → A): a caller that needs a feedback-driven release (B: "walk until the minimap says
stop") sends `walk(dir, upper_bound)` and calls `release_all()` when the feedback arrives. The board pre-empts the
running schedule and the pending play returns ABORTED (C3, PA-adj2-D1). No protocol extension is needed. If a key
must stay held across commands, that is a new op behind `ver`/`op` (decisions.md PA-D5 undo).

**Notifications**, board → PC, on `89f7c2ca-89b5-4234-905c-d4a931feaa3b` (PC subscribes with `start_notify`):

| `kind` | Name | Layout after `ver, kind, seq(u16)` | Total |
|---|---|---|---|
| `0x81` | ACCEPTED | `t0_us` u32 (board `esp_timer_get_time()` low 32 bits at schedule start) | 8 |
| `0x82` | DONE | `status` u8 · `fail_step` u8 (`0xFF` none) · `rc` i16 · `t0_us` u32 · `n` u8 · n × `late_us` u16 (actual send − scheduled, saturating at 65535) | 13 + 2n |
| `0x83` | REJECTED | `reason` u8 | 5 |
| `0x84` | PONG | `itvl` u16 (1.25 ms units, the *current* interval: refreshed on each conn-param update, not the `onConnect` copy) · `latency` u16 · `timeout` u16 (10 ms units) · `mtu` u16 · `flags` u8 (bit0 bonded, bit1 encrypted, bit2 authenticated, bit3 HID input report subscribed by the peer that wrote the PING; bits 4–7 reserved, sent 0, ignored by the PC) · `board_us` u32 | 17 |

DONE `status`: `0` OK · `1` NOTIFY_FAILED (HID notify returned false at `fail_step`, `rc` = NimBLE code; board then
tries one all-up report and abandons the schedule) · `2` DISCONNECTED · `3` ABORTED (by RELEASE_ALL).
**DONE fields by case (PA-rev m6).** `n` counts the schedule steps the board attempted to send and `late_us[i]` is
step i's; the extra all-up report sent after a failure or an abort is not a step and is not counted. `fail_step` is
`0xFF` and `rc` is `0` unless `status` is `1`. `t0_us` is the command's ACCEPTED `t0_us`, or `0` if no ACCEPTED was
sent.
- `0` OK (PLAY): `n` = the PLAY's step count.
- `1` NOTIFY_FAILED at step k: `fail_step` = k, `rc` = the NimBLE code (`−1` when the HID-report lookup failed,
  F5), `n` = k + 1 (the failing step counts; its `late_us` is recorded before the send).
- `3` ABORTED: `n` = the steps sent before the abort (`0` when aborted during the start jitter, after ACCEPTED). A
  queued PLAY answered ABORTED before it started (no ACCEPTED) has `n = 0` and `t0_us = 0`.
- `2` DISCONNECTED is reserved: no DONE is sent after a disconnect (F5).
- RELEASE_ALL: `n = 1`, its one step being the all-up report, sent at once: `t0_us` = board time when that send
  starts and `late_us = [0]`; a failed send gives status `1` with `fail_step` 0 and `rc` as above.
REJECTED `reason`: `1` BAD_VERSION · `2` BAD_LENGTH · `3` BAD_SCHEDULE · `4` QUEUE_FULL · `5` UNKNOWN_OP ·
`6` HID_NOT_SUBSCRIBED (PA-adj1c-D1 → A: the peer that wrote the PLAY is not subscribed to the HID input report, so
NimBLE's notify would return true while Windows gets no key; sent by the executor before playing, never by
`proto::parse`). The PC maps every reason to `InputError.REJECTED`.
RELEASE_ALL is answered by DONE (`n = 1`, its one step being the all-up report; fields above).

Size limits: the longest command is 53 bytes and the longest notification 45 bytes. Over-MTU notifications are
truncated silently by NimBLE while `sendValue` returns true (`ble_att.c:421-432`, notes/PA-adj1.md row 2), so the PC
**requires PONG `mtu` ≥ 56 (53 + 3) at connect, else `connect()` is a Failure** (PA-adj1-D1 → A; P4). PONG `mtu` is
the board's live ATT MTU, the one its truncation uses. The PC also reads `client.mtu_size` (bleak
`__init__.py:617`) at session start and refuses (Failure) any PLAY longer than `mtu_size − 3`.

Shared golden vectors: `firmware/test/vectors.json` is the single source used by both the C++ host test (F4) and
the Python tests (P1). A format change edits that file first. Two entry shapes:
- byte vectors: `{"name", "hex", "expect": {...}}` (decoded fields, or `{"reject": <reason>}` for a command the
  board must reject). F4 parses every command and encodes every notification; P1 encodes every valid command and
  decodes every notification. Schedule-rule rejects (n = 0, n = 17, bit 7, two keys in one step, last mask ≠ 0,
  Σ > 100 000) also carry `"steps"`, so P1 checks `validate_schedule` on the same case.
- PC-only vectors: `{"name", "pc_only": true, "steps": [[delta_100us, mask], ...], "expect": {"error": "<rule>"}}`
  for rules a wire frame cannot express (the per-step delta cap). P1 runs them; the F4 C++ test skips them.

Behaviour fixed by rulings (implemented in P4/P5):
- **`release_all()` pre-empts (PA-adj2-D1 → A).** `BleLink.release_all()` and `InputLayer.release_all()` may be
  called from another thread while a `play()` is in flight. It bypasses the one-command-in-flight rule, writes
  RELEASE_ALL at once, and returns when its own DONE arrives. The pending `play()` returns `Failure(ABORTED)`.
  `InputLayer.release_all()` bypasses timing.
- **Feedback release (PA-D5 → A).** A caller that releases on feedback (B: walk until vision says arrived) calls
  `walk(dir, upper_bound)` and then `release_all()` from its feedback thread. The pending walk returns
  `Failure(ABORTED)`, which is the expected result there. If the feedback never comes, the upper bound releases
  anyway.
- **Release after an uncertain failure (PA-adj1b-D1 → A).** When `play()` returns `NOTIFY_FAILED`, `ACK_TIMEOUT` or
  `WRITE_FAILED`, `InputLayer` sends one `release_all()` before it returns that Failure (its own result is not
  returned and does not replace the original error). It does not do this after `REJECTED`, `TOO_LONG` or `ABORTED`.
  After `LINK_LOST` no release can be sent (the link is gone; every call returns `NOT_CONNECTED` until `connect()`
  succeeds again, P4 Session state).
- **Session end (PA-rev m3, PA-rev3a-D2 → A).** `close()` fails every pending call with `NOT_CONNECTED` (not a
  fault; no release follows, P5). `connect()` on a live session returns `Failure("already connected")` and leaves
  the session untouched.
- **Walk over the per-step cap.** `InputLayer.walk()` returns `Failure(TOO_LONG)` without sending when
  `actions.walk()` returns a Failure (C1 per-step delta ≤ 65 535).
- **Sequence over 8 keys (PA-rev m2).** `actions.sequence()` returns a Failure for more than 8 keys (each key is a
  down and an up step, so 9 keys would exceed C1's 16 steps). `InputLayer.sequence()` then returns
  `Failure(TOO_LONG)` before any wait and without sending, as `walk()` does. Phase 1 needs at most 5 (the soak, H2).

Harness modules live in `src/input/harness/` (`listener.py` H1, `probe.py` V1, `soak.py` and `faults.py` H2,
`analyze.py` H3, `realism.py` H4, `session_starts.py` V2). Tests in `tests/` mirror the module paths. Firmware in
`firmware/Helix_BLE/` plus a host-compiled protocol test in `firmware/test/`.

### C4. Timing model (PAr §4b; sources in the Sources section) — values in ms

Every value is drawn on the PC from one seeded `numpy.random.Generator`, independently (gives "no fixed rhythm",
spec:L48, PAr §4b notes), quantised to 100 µs, and logged with its type. Truncation is by rejection sampling, so the
KS reference CDF is the truncated CDF `(F(x) − F(a)) / (F(b) − F(a))` on `[a, b]` (PAr §4b "KS tests on truncated
draws must use the truncated CDF").

| Type | Family | Parameters (derived numbers shown) | Truncation | Source |
|---|---|---|---|---|
| HOLD (tap; also the second key of a chord, and each key of a sequence) | lognormal | mean 116, SD 24 → σ_ln = √ln(1+(24/116)²) = 0.2047, μ_ln = ln 116 − σ²/2 = 4.7326 | [60, 250] | Dhakal et al. 2018 Table 3 "All" 116.25 / 23.88 (PAr §4.1); family is a judgement |
| GAP (key-down → next key-down inside one action) | 60 + lognormal | lognormal part mean 160, SD 90 → σ_ln = 0.5243, μ_ln = 4.9377 | [60, 1000] (total) | Dhakal 2018 p.5 "lower bound of about 60 ms", Trained mean 223.55 (PAr §4.2); SD 90 a judgement |
| CHORD_OFFSET (key 1 down → key 2 down) | lognormal | median 25 → μ_ln = ln 25 = 3.2189, σ_ln = 0.5 | [8, 100] | **Judgement, no direct source** (PAr §4.3): anchored to Dhakal rollover "30 ms, on average, and up to 100 ms" |
| RELEASE_LAG (key 2 up → key 1 up, chords) | uniform | U(0, 60) | — | Judgement (PAr §4b row C) |
| REACTION (drawn as stimulus → first key-down; applied as stimulus → send, see the rule below) | ex-Gaussian | μ = 195, σ = 20, τ = 35 (mean 230, SD 40.3); scipy `exponnorm(K=τ/σ=1.75, loc=μ, scale=σ)` | [110, 1000] | Woods et al. 2015 Table 2 mean 230.8, within-subject SD 40.0 (PAr §4.4, fetch-summary grade); split μ/σ/τ is a judgement |
| WALK (long hold, intended T from the caller) | T + N(0, kT² + σ²ᵢ) | √k = 0.04, σᵢ = 65 | result ≥ T/2 | Laje et al. 2011 generalised Weber law, values read off figures (PAr §4.5, inferred) |

Rules from PAr §4b and §5:
- **Reaction is PC-only:** `wait = max(0, R − elapsed_since_stimulus)` before sending; it is not in the schedule.
  So R is applied from stimulus to **send**, and the delivered reaction (stimulus → first key-down) is R plus the
  send → first key-down latency (V1 M7 total; it includes F5's start jitter), or longer when the wait was clamped
  at 0 (PA-rev m23). This is by design in Phase 1, not corrected for; H4 reports the residual and D1's as-built
  section states it.
- **Chord key order is functional:** arrow then `E` (teleport), `DOWN` then `ALT` (drop). Key 2's hold is HOLD; key 1
  is released RELEASE_LAG after key 2.
- **Sequence with a repeated key:** if key *i+1* equals key *i* and key *i*'s HOLD would reach past key *i+1*'s down
  minus 15 ms, key *i*'s up is clipped to that point and its sample is logged as type `hold_clipped`, counted in the
  report. Its `chosen_ms` is still the drawn HOLD float (unclipped) and stays in HOLD's KS (PA-rev m13: only long
  draws get clipped, so dropping them would bias the KS against its own model); its **scheduled** value, the
  clipped interval its `step_from`→`step_to` steps span in `steps`, is what H4's delivered check pairs it against
  (PA-rev I7).
- **Chosen value = the generator's float (PAr-D1 ruling C).** `Sample.ms` is the float the generator returned,
  before encoding; the realism tests use it. The 100 µs wire value is logged next to it (`wire_100us` =
  round(ms × 10); for `hold_clipped` it is the quantised draw, and the played interval is the `steps` span
  `step_from`→`step_to`, PA-rev3b m-h), and P3's test catches encoding errors (each sample's span in `steps` sums to
  its `wire_100us`, smaller for `hold_clipped`). For reaction, the chosen value is the drawn R, not the
  wait `max(0, R − elapsed)` (`PAr-D1.md:117-118`).
- No per-session "persona" scaling in Phase 1 (PAr §4b).

### C5. Soak log format (JSONL, one object per line) — **interface** for H2 → H3/H4

Written by the soak driver to `data/soak/<run_id>/` (gitignored by `.gitignore` `data/`):
- `commands.jsonl`: `{"seq", "action", "stimulus_ns", "steps":[[delta_100us, mask],...],
  "samples":[{"type", "chosen_ms" (generator float), "wire_100us", "index", "step_from", "step_to"},...],
  "reaction_ms" (drawn R), "waited_ms", "sent_ns", "written_ns", "accepted_ns", "done_ns", "t0_us", "late_us":[...],
  "status", "error", "bytes"}`. `step_from`/`step_to` name the two schedule steps an interval spans, so H4 can pair
  each chosen interval with the measured one. `sent_ns`, `written_ns`, `accepted_ns`, `done_ns` come from the
  `SendReport` (C3), `t0_us`/`late_us` from its DONE. For a Failure the timing fields are null; `status`/`error`
  carry the InputError (PA-fix1c-D1-adj-D1 → A). For a Failure, `steps`, `samples`, `reaction_ms`, `waited_ms` and
  `bytes` are null too (InputLayer returns only the InputError, C3); H3 and H4 read only `seq`, `action`,
  `stimulus_ns`, `status` and `error` of such a row (PA-rev3a N2). A command the soak driver never sent because the
  sink did not get the foreground back (H2 focus policy, PA-rev m15; PA-fix3e-D1 → A) has `status` and `error`
  `"FOCUS_LOST"` (a harness value, not an InputError: no InputLayer call was made), `stimulus_ns`, `steps`,
  `samples`, `reaction_ms`, `waited_ms`, the timing fields and `bytes` null, and is always the run's last row. It is
  not a command for any H3 or H4 check (Delivery and its failed commands, Latency, Faults, Stuck keys, KS,
  Delivered timing): each skips it, and only H3 reads it, to print `FOCUS_LOST at seq <n>` (PA-rev3b m-e).
- `pongs.jsonl`: `{"qpc_ns", "itvl_units", "latency", "timeout_units", "mtu", "flags", "board_us"}` for every
  keepalive PONG (every 250 ms), so a mid-soak CI change and the board/PC clock offset are visible
  (`PAr-D1.md:91-92`).
- `keys.jsonl` (listener): `{"qpc_ns", "vk", "down": bool, "injected": bool, "tick_ms", "repeat": bool}`; `repeat` is
  true for a down while that key is already down (OS auto-repeat, PAr §2.3); repeats are logged but are not
  transitions.
- `faults.jsonl`: `{"injected_ns", "kind", "reported_ns", "error", "launch_ns", "fault_seen_ns", "failure_ns"}`, all
  `*_ns` `perf_counter_ns` (PA-rev I5; PA-fix3d-D1 → A): `injected_ns` = the moment the fault takes effect
  (`reset_board`: esptool's reset line; `bluetooth_off_on`: just before `set_state_async(OFF)`, kept only if that
  call returns `RadioAccessStatus.ALLOWED`, or the marker line the `Disable-PnpDevice` fallback prints right before
  the cmdlet (kept only if the cmdlet succeeded, PA-rev4a m2), PA-rev3b G3), null if that moment was not observed;
  `launch_ns` = esptool start (null for `bluetooth_off_on`); `fault_seen_ns` = the first `BleLink.faults()` entry
  after `injected_ns`; `failure_ns` = the
  first `Failure` returned to the driver after `injected_ns`; `reported_ns` = the earlier of the two (null if
  neither); `error` = the InputError of whichever came first. Every injection attempt writes its entry, also when
  the injector fails before the fault takes effect (no esptool run, no reset line, radio control refused with no
  fallback); a null `injected_ns` makes `fault_seen_ns`, `failure_ns`, `reported_ns` and `error` null too, so H3's
  Faults check FAILs the entry, printed with its `kind` (PA-rev3b G2).
- `session.json`: run id, seed, git SHA, MTU, PONG fields, CI in ms, start/end ns, process-check result,
  `focus_pauses` (`[[start_ns, end_ns], ...]`, perf_counter_ns, one per pause of H2's focus policy that ended with
  the sink back in the foreground, `[]` when there was none; PA-rev m15, PA-rev3b m-f; PA-fix3e-D1 → A).
  H2 writes it on every exit path (normal end, any abort incl. `FOCUS_LOST`, Ctrl-C), so its end ns always exists;
  on a `FOCUS_LOST` abort the end ns is the abort moment, which follows the failed 10 s pause at once (that row's
  own timestamps are null; PA-rev3b m-f).
- `link.log` (plain text, the one non-JSONL file; PA-rev m24/m8): every WARNING-or-higher record of logger
  `src.input.link` (P4's undecodable-notification WARNING with the bytes in hex, P4's encode ERROR), one per line,
  `%(created).6f %(perf_ns)d %(levelname)s %(message)s` (`created` is `time.time()` seconds, wall clock, for
  reading; `perf_ns` is `time.perf_counter_ns()` stamped by H2's handler filter, the clock of every other C5 file;
  PA-fix4b-D1 → B). Written by H2's FileHandler; H3 does not parse it.
  It exists so that offline an `ACK_TIMEOUT` that follows a WARNING for the same seq (a malformed frame, matched by
  seq or, when the hex carries none, by time between that command's `stimulus_ns` and the next one's, since a
  Failure row's timing fields are null) can be told from one with none (a lost notification).

Both the chosen values (`samples`) and the PC-measured timestamps (`keys.jsonl`) are logged for every event, so
all PAr-D1-dependent criteria live in Task H4 alone.

### Task H1: Keystroke listener + test window ⌨

**Files:** create `src/input/harness/__init__.py`, `src/input/harness/listener.py`; tests `tests/input/test_listener.py`.

Verified API facts (LowLevelKeyboardProc, Microsoft Learn, see Sources):
- "This hook is called in the context of the thread that installed it. The call is made by sending a message to the
  thread that installed the hook. Therefore, the thread that installed the hook must have a message loop."
- "If the hook procedure times out, the system passes the message to the next hook. However, on Windows 7 and later,
  the hook is silently removed without being called." The maximum timeout is 1000 ms.
- "If the hook procedure processed the message, it may return a nonzero value to prevent the system from passing the
  message to the rest of the hook chain or the target window procedure."
- KBDLLHOOKSTRUCT `flags` bit 4 = injected; `time` is tick-based (10–16 ms, PAr §2.3), so timestamps use
  `time.perf_counter_ns()` inside the callback.

Design:
- A pure `TransitionTracker` (testable): input `(vk, is_down)`; output a transition, or `repeat` (a down while
  already down, i.e. OS auto-repeat, counted as a non-event, PAr §2.3 / §7), or `orphan_up`.
- The hook thread installs `SetWindowsHookExW(WH_KEYBOARD_LL=13, proc, GetModuleHandleW(None), 0)` and runs a
  `GetMessageW` loop (*UNVERIFIED at planning: the exact ctypes signatures and the hMod argument; verify against
  https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw before coding*). The
  callback only timestamps and pushes to a `queue.SimpleQueue`, then returns at once (the timeout rule). A writer
  thread drains the queue into `keys.jsonl` (C5).
- **Blocking (default on, `--no-block` to turn it off) *(PA-D7 → A; decisions.md PA-D7)*:** for the seven C2 VKs
  the callback returns 1 after recording, so the keys reach no window procedure (`lowlevelkeyboardproc.md:94`: the
  raw markdown behind the Learn page in Sources, github.com/MicrosoftDocs/win32
  `desktop-src/winmsg/lowlevelkeyboardproc.md`, re-read 2026-10-21). Every other VK, and every VK under
  `--no-block`, goes on through `CallNextHookEx`. The decision is a pure function `should_block(vk, block) -> bool`,

### Task H4: Analysis: timing realism + delivered timing — **the PAr-D1 criteria (ruling C)**

**Files:** create `src/input/harness/realism.py`; tests `tests/input/test_realism.py`.

**This is the only task whose pass criteria depend on PAr-D1.** It implements ruling C (`PAr-D1.md:27-35`,
`:107-118`). If the ruling is ever revisited, only this task changes; the logs (C5) already hold chosen and measured
values for every interval.

- **Timing realism** (spec:L60 as amended): for each type HOLD, GAP, CHORD_OFFSET, REACTION, take the **chosen**
  values (`samples[].chosen_ms`, the generator floats, never `wire_100us`; for REACTION the drawn R, i.e.
  `reaction_ms`, never `waited_ms`). HOLD's values are every HOLD generator float, `hold_clipped` samples' drawn
  floats included (C4, PA-rev m13). Run `scipy.stats.kstest(values, truncated_cdf(type))` with n ≥ 1 000. PASS
  if `pvalue ≥ 0.01` (KS, α = 0.01). Gap-run test: the stream of chosen GAP values (gaps within one action) in
  soak order; PASS if no window of 5 consecutive values occurs twice anywhere (exact float equality).
- **Delivered timing** (spec:L59 as amended): pair every HOLD, WALK, `hold_clipped`, CHORD_OFFSET and GAP sample
  with its measured counterpart through `step_from/step_to` → the matching listener transitions (transitions only;
  repeats excluded). For holds (all three hold types) that is the key's down→up; for chord offsets and gaps, the
  down→down. Each of the five is its own share, gated (PA-rev I7: spec:L59 "each hold", spec:L13 "walking is
  holding an arrow"; PAr-D1 has no walk exclusion): WALK holds (20% of the soak's commands, H2, and the only holds
  that can exceed 250 ms) and clipped holds are gated next to HOLD, never mixed into it, so neither dilutes the HOLD share.
  The reference is `chosen_ms`, except for `hold_clipped`, whose reference is its scheduled (clipped) interval
  from `steps` (C4), since the chosen float was never meant to be played. PASS per share if
  `|measured − reference| ≤ 20 ms` for ≥ 95% of its pairs. Only `hold_clipped` can be empty in a soak (no repeated
  key long enough to clip); then it prints `hold_clipped n = 0` and is not gated. **Chord order:** PASS only if, for every chord,
  the second key's down is never seen before the first key's down (0 violations). An unpairable interval (a
  missing transition) counts as a miss here and is also a Delivery failure in H3.
- **Reported, not gated** (`PAr-D1.md:109-111`): reaction residual (first key-down − `stimulus_ns` − R, i.e. the send → key-down latency
  when the wait was not clamped, C4 / PA-rev m23; p50/p99), gaps
  between actions, the measured-value KS D per type (a CI/jitter diagnostic), the chord-collapse rate (measured
  offset < 1 ms), `hold_clipped` count, WALK error stats, the CI history from `pongs.jsonl`, sample counts.
- [ ] **Step 1: failing tests**: chosen samples drawn from the model PASS KS; samples from a shifted model FAIL;
  the KS entry point takes `samples` and reads `chosen_ms` (a test feeds a sample whose `wire_100us` differs from

  FAILS the order check; reaction uses `reaction_ms` not `waited_ms`; a log ending in a `FOCUS_LOST` row (null
