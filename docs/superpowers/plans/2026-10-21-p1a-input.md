# Plan: Phase 1 · Feature A — Input over Bluetooth

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development`. One fresh implementer
> per task, in order. Each task is TDD (`superpowers:test-driven-development`): write the listed tests first, watch
> them fail, then implement. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the PC presses, holds and releases the bot's keys (arrows, `E`, `Alt`, `Space`, chords, holds) through the
ESP32-S3 "Guiness" acting as a real BLE HID keyboard, with human-like timing chosen on the PC, every failure visible
to the caller, and every reliability target in spec A met on real hardware.

**Architecture:** the PC samples every timing value (seeded RNG) and sends one *action* as a timed schedule of key
states over the custom GATT command characteristic. The firmware's `onWrite` only enqueues. `loop()` dequeues, plays
the schedule with `esp_timer` µs timing, and sends each HID report through the non-coalescing
`notify(value, len, connHandle)` path. It acks over the notify characteristic. A PC-side low-level keyboard hook
records what Windows actually receives; a soak harness logs both the chosen and the measured values, and an
analysis step checks each target.

## Contracts fixed by this plan (the interfaces every task builds against)

### C1. Wire protocol v1 *(PA-D1 → A, binary v1; decisions.md PA-D1)* — **interface**

Little-endian. Board ⇄ PC over the existing custom service `a723b49a-2b53-46a6-a2db-02bb9e9a577c` (spec:L38).

**Commands**, PC → board, *write with response* (`response=True`) to `61adcd67-20e9-4c38-b1d0-879445c5b732`:

| Off | Size | Field |
|---|---|---|
| 0 | 1 | `ver` = `0x01` |
| 1 | 1 | `op`: `0x01` PLAY (queued) · `0x02` RELEASE_ALL (abort + all-up) · `0x03` PING (answered at once from `onWrite`) |
| 2 | 2 | `seq` u16, PC-assigned, increments, wraps |
| 4 | 1 | PLAY only: `n` steps, 1..16 |
| 5 | 3·n | PLAY only: per step `delta` u16 (100 µs units, from the previous step; step 0 from schedule start) + `mask` u8 |

`mask` bits: `0` LEFT · `1` RIGHT · `2` UP · `3` DOWN · `4` E · `5` ALT · `6` SPACE · `7` must be 0.

PLAY is valid only if all of these hold (checked on **both** sides; the board rejects, the PC never sends):
length is exactly `5 + 3n`; `1 ≤ n ≤ 16`; bit 7 clear in every mask; **each step changes exactly one key** relative to
the previous state (the state before step 0 is all-up), so every report is exactly one Windows key transition and
the order is unambiguous; the **last mask is 0** (closed schedule, PA-D5 → A); `Σ delta ≤ 100 000`
(10 s). On the PC only, also: **every step's `delta` ≤ 65 535** (6.5535 s, PA-adj1-D2 → A). A u16 field cannot carry
more, so the board never sees a violation. `validate_schedule` / `encode_play` return a `Failure` naming the
"per-step delta" rule and never let `struct.pack` raise. A walk is two steps, so the longest walk is 6.5535 s.
Longer walks are chained.

Closed schedules (PA-D5 → A): a caller that needs a feedback-driven release (B: "walk until the minimap says
stop") sends `walk(dir, upper_bound)` and calls `release_all()` when the feedback arrives. The board pre-empts the
running schedule and the pending play returns ABORTED (C3, PA-adj2-D1). No protocol extension is needed. If a key
must stay held across commands, that is a new op behind `ver`/`op` (decisions.md PA-D5 undo).

**Notifications**, board → PC, on `89f7c2ca-89b5-4234-905c-d4a931feaa3b` (PC subscribes with `start_notify`):

| `kind` | Name | Layout after `ver, kind, seq(u16)` | Total |
|---|---|---|---|
| `0x81` | ACCEPTED | `t0_us` u32 (board `esp_timer_get_time()` low 32 bits at schedule start) | 8 |
| `0x82` | DONE | `status` u8 · `fail_step` u8 (`0xFF` none) · `rc` i16 · `t0_us` u32 · `n` u8 · n × `late_us` u16 (actual send − scheduled, saturating at 65535) | 13 + 2n |
| `0x83` | REJECTED | `reason` u8 | 5 |
| `0x84` | PONG | `itvl` u16 (1.25 ms units, the *current* interval: refreshed on each conn-param update, not the `onConnect` copy) · `latency` u16 · `timeout` u16 (10 ms units) · `mtu` u16 · `flags` u8 (bit0 bonded, bit1 encrypted, bit2 authenticated, bit3 HID input report subscribed by the peer that wrote the PING; bits 4–7 reserved, sent 0, ignored by the PC) · `board_us` u32 | 17 |

DONE `status`: `0` OK · `1` NOTIFY_FAILED (HID notify returned false at `fail_step`, `rc` = NimBLE code; board then
tries one all-up report and abandons the schedule) · `2` DISCONNECTED · `3` ABORTED (by RELEASE_ALL).
REJECTED `reason`: `1` BAD_VERSION · `2` BAD_LENGTH · `3` BAD_SCHEDULE · `4` QUEUE_FULL · `5` UNKNOWN_OP ·
`6` HID_NOT_SUBSCRIBED (PA-adj1c-D1 → A: the peer that wrote the PLAY is not subscribed to the HID input report, so
NimBLE's notify would return true while Windows gets no key; sent by the executor before playing, never by
`proto::parse`). The PC maps every reason to `InputError.REJECTED`.
RELEASE_ALL is answered by DONE (`n = 1`, its one step being the all-up report).

Size limits: the longest command is 53 bytes and the longest notification 45 bytes. Over-MTU notifications are
truncated silently by NimBLE while `sendValue` returns true (`ble_att.c:421-432`, notes/PA-adj1.md row 2), so the PC
**requires PONG `mtu` ≥ 56 (53 + 3) at connect, else `connect()` is a Failure** (PA-adj1-D1 → A; P4). PONG `mtu` is
the board's live ATT MTU, the one its truncation uses. The PC also reads `client.mtu_size` (bleak
`__init__.py:617`) at session start and refuses (Failure) any PLAY longer than `mtu_size − 3`.

Shared golden vectors: `firmware/test/vectors.json` is the single source used by both the C++ host test (F4) and
the Python tests (P1). A format change edits that file first. Two entry shapes:
- byte vectors: `{"name", "hex", "expect": {...}}` (decoded fields, or `{"reject": <reason>}` for a command the
  board must reject). F4 parses every command and encodes every notification; P1 encodes every valid command and
  decodes every notification. Schedule-rule rejects (n = 0, n = 17, bit 7, two keys in one step, last mask ≠ 0,
  Σ > 100 000) also carry `"steps"`, so P1 checks `validate_schedule` on the same case.
- PC-only vectors: `{"name", "pc_only": true, "steps": [[delta_100us, mask], ...], "expect": {"error": "<rule>"}}`
  for rules a wire frame cannot express (the per-step delta cap). P1 runs them; the F4 C++ test skips them.

Behaviour fixed by rulings (implemented in P4/P5):
- **`release_all()` pre-empts (PA-adj2-D1 → A).** `BleLink.release_all()` and `InputLayer.release_all()` may be
  called from another thread while a `play()` is in flight. It bypasses the one-command-in-flight rule, writes
  RELEASE_ALL at once, and returns when its own DONE arrives. The pending `play()` returns `Failure(ABORTED)`.
  `InputLayer.release_all()` bypasses timing.
- **Feedback release (PA-D5 → A).** A caller that releases on feedback (B: walk until vision says arrived) calls
  `walk(dir, upper_bound)` and then `release_all()` from its feedback thread. The pending walk returns
  `Failure(ABORTED)`, which is the expected result there. If the feedback never comes, the upper bound releases
  anyway.
- **Release after an uncertain failure (PA-adj1b-D1 → A).** When `play()` returns `NOTIFY_FAILED`, `ACK_TIMEOUT` or
  `WRITE_FAILED`, `InputLayer` sends one `release_all()` before it returns that Failure (its own result is not
  returned and does not replace the original error). It does not do this after `REJECTED`, `TOO_LONG` or `ABORTED`.
  After `LINK_LOST` no release can be sent (the link is gone).
- **Walk over the per-step cap.** `InputLayer.walk()` returns `Failure(TOO_LONG)` without sending when
  `actions.walk()` returns a Failure (C1 per-step delta ≤ 65 535).

`tests/` mirror the module paths. Firmware in `firmware/Helix_BLE/` plus a host-compiled protocol test in
`firmware/test/`.

### C4. Timing model (PAr §4b; sources in the Sources section) — values in ms

Every value is drawn on the PC from one seeded `numpy.random.Generator`, independently (gives "no fixed rhythm",
spec:L48, PAr §4b notes), quantised to 100 µs, and logged with its type. Truncation is by rejection sampling, so the
KS reference CDF is the truncated CDF `(F(x) − F(a)) / (F(b) − F(a))` on `[a, b]` (PAr §4b "KS tests on truncated
draws must use the truncated CDF").

| Type | Family | Parameters (derived numbers shown) | Truncation | Source |
|---|---|---|---|---|
| HOLD (tap; also the second key of a chord, and each key of a sequence) | lognormal | mean 116, SD 24 → σ_ln = √ln(1+(24/116)²) = 0.2047, μ_ln = ln 116 − σ²/2 = 4.7326 | [60, 250] | Dhakal et al. 2018 Table 3 "All" 116.25 / 23.88 (PAr §4.1); family is a judgement |
| GAP (key-down → next key-down inside one action) | 60 + lognormal | lognormal part mean 160, SD 90 → σ_ln = 0.5243, μ_ln = 4.9377 | [60, 1000] (total) | Dhakal 2018 p.5 "lower bound of about 60 ms", Trained mean 223.55 (PAr §4.2); SD 90 a judgement |
| CHORD_OFFSET (key 1 down → key 2 down) | lognormal | median 25 → μ_ln = ln 25 = 3.2189, σ_ln = 0.5 | [8, 100] | **Judgement, no direct source** (PAr §4.3): anchored to Dhakal rollover "30 ms, on average, and up to 100 ms" |
| RELEASE_LAG (key 2 up → key 1 up, chords) | uniform | U(0, 60) | — | Judgement (PAr §4b row C) |
| REACTION (stimulus → first key-down) | ex-Gaussian | μ = 195, σ = 20, τ = 35 (mean 230, SD 40.3); scipy `exponnorm(K=τ/σ=1.75, loc=μ, scale=σ)` | [110, 1000] | Woods et al. 2015 Table 2 mean 230.8, within-subject SD 40.0 (PAr §4.4, fetch-summary grade); split μ/σ/τ is a judgement |
| WALK (long hold, intended T from the caller) | T + N(0, kT² + σ²ᵢ) | √k = 0.04, σᵢ = 65 | result ≥ T/2 | Laje et al. 2011 generalised Weber law, values read off figures (PAr §4.5, inferred) |

Rules from PAr §4b and §5:
- **Reaction is PC-only:** `wait = max(0, R − elapsed_since_stimulus)` before sending; it is not in the schedule.
- **Chord key order is functional:** arrow then `E` (teleport), `DOWN` then `ALT` (drop). Key 2's hold is HOLD; key 1
  is released RELEASE_LAG after key 2.
- **Sequence with a repeated key:** if key *i+1* equals key *i* and key *i*'s HOLD would reach past key *i+1*'s down
  minus 15 ms, key *i*'s up is clipped to that point and its sample is logged as type `hold_clipped` (excluded from
  KS, counted in the report).
- **Chosen value = the generator's float (PAr-D1 ruling C).** `Sample.ms` is the float the generator returned,
  before encoding; the realism tests use it. The 100 µs wire value is logged next to it (`wire_100us`), and the
  per-interval residual check (H4) catches encoding errors. For reaction, the chosen value is the drawn R, not the
  wait `max(0, R − elapsed)` (`PAr-D1.md:117-118`).
- No per-session "persona" scaling in Phase 1 (PAr §4b).

### C5. Soak log format (JSONL, one object per line) — **interface** for H2 → H3/H4

Written by the soak driver to `data/soak/<run_id>/` (gitignored by `.gitignore` `data/`):
- `commands.jsonl`: `{"seq", "action", "stimulus_ns", "steps":[[delta_100us, mask],...],
  "samples":[{"type", "chosen_ms" (generator float), "wire_100us", "index", "step_from", "step_to", "first_key"?},...],
  "reaction_ms" (drawn R), "waited_ms", "sent_ns", "written_ns", "accepted_ns", "done_ns", "t0_us", "late_us":[...],
  "status", "error", "bytes"}`. `step_from`/`step_to` name the two schedule steps an interval spans, so H4 can pair
  each chosen interval with the measured one.
- `pongs.jsonl`: `{"qpc_ns", "itvl_units", "latency", "timeout_units", "mtu", "flags", "board_us"}` for every
  keepalive PONG (every 250 ms), so a mid-soak CI change and the board/PC clock offset are visible
  (`PAr-D1.md:91-92`).
- `keys.jsonl` (listener): `{"qpc_ns", "vk", "down": bool, "injected": bool, "tick_ms", "repeat": bool}`; `repeat` is
  true for a down while that key is already down (OS auto-repeat, PAr §2.3); repeats are logged but are not
  transitions.
- `faults.jsonl`: `{"injected_ns", "kind", "reported_ns", "error"}`.
- `session.json`: run id, seed, git SHA, MTU, PONG fields, CI in ms, start/end ns, process-check result.

Both the chosen values (`samples`) and the PC-measured timestamps (`keys.jsonl`) are logged for every event, so
all PAr-D1-dependent criteria live in Task H4 alone.
