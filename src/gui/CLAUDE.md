- Ropes in the editor (H91, H94; plan `docs/superpowers/plans/2026-11-10-rope-fix.md` Task 3). `MapEditorState` holds `ropes` (`List[RopeMark]`, map coordinates), `selected_rope` (an index into `ropes`, drawn thicker), `rope_extra` (the loaded rope file's unknown keys, which a save keeps) and `rope_file_read` (a rope file was read at load without error, or this editor has written one since; `_load` assigns it on every load, so a flag never outlives its map, and a map with no rope file leaves it false). The dirty flag (the `_saved_ropes` baseline), `_renderRopes` (yellow lines, called by `_renderNodes` before the dots), the red `rope_keepout` rings and the Save block all follow from `state.ropes` alone. Keep-out: `_onCanvasClick` tries the node hit first, then `near_rope_end`, then `_placeNode`; a refused click places nothing and writes `Not placed: ...` (with the free x's from `free_x`) through `_setStatus`, the one writer of the status line below the canvas. `_validateForSave` blocks, after the empty-rotation block and before the warnings, when a node is near a rope end. Files: `_writeTo` writes the CSV, then the rope file when ropes are marked or `rope_file_read` is true (so ropes deleted from a good file stay deleted and its unknown keys are kept); a map with neither stays one file. A rope-file failure shows "Save failed" naming it and leaves the title dirty (the CSV is already written; the baseline is taken only when both writes succeed). `_load` reads the rope file only after the CSV, the size and the bounds checks have passed. A bad rope file does not stop the load: the nodes open with no ropes, the editor is clean, and a box titled "Rope file not loaded" gives the reader's message and says the file is replaced only by marking ropes and saving. A save with no ropes marked, while the rope file beside the file being written is damaged, first asks "This map's rope file is damaged and no ropes are marked. Closing the window (`onAppClose`, :780, spec 5.5 "Closing the app mid-run", H79): with no worker the hosted view goes, then the window, at once; with one it calls `session.stop("window_close")`, shows `CLOSING_TEXT` ("Closing - waiting for the run to finish cleaning up...", or `CLOSING_CONNECT_TEXT` when the state was still `connecting`; a Stop pressed during the connection attempt first makes the state `stopping`, so the close then shows the first text) and polls every 100 ms (`_pollClose`, :826) until the worker has ended, however long that takes: there is no time limit and nothing is printed. A press while it waits (`_closePressedAgain`) does nothing within `CLOSE_WAIT_S` (10 s, read from the `clock` keyword) of the first press or once the worker has ended; later it asks `askCloseAnyway()`: Yes destroys the window at once (the worker is a daemon and dies with the process), No keeps waiting, and every later press asks again. `_asking` is set while the box is open and makes `_pollClose` wait without destroying the window, because Tk's timers do run inside `askyesno`'s own loop on Windows (RDO110-5-R's probe: a 100 ms `after` loop ran 18 times in 2 s), so the guard is needed. Garbage collection during a run (RT-8a I1, ruling RT-8a-review-D1 A): Python's cycle collector runs on whichever thread allocates past its threshold, and on the worker it could free a Tk object whose `__del__` calls Tcl, which waits for the Tk thread with no timeout and can deadlock it on a lock both take (the event queue's). So Start calls `gc.collect()`, `gc.disable()` and `gc.freeze()` on the Tk thread just before `worker.start()`; while the worker lives the drain calls `gc.collect()` every `GC_EVERY_POLLS` (10) steps, about once a second, and because what existed at Start is frozen, that collection walks only what the run has made since (ruling orch 108; measured with the app's modules imported, Python 3.14.0: a full collection of the app's ~123 500 objects takes about 23 ms, one just after the freeze under 0.1 ms, one with 50 000 objects made since about 1.5 ms). `_clearWorker` (:595) unfreezes, collects once on the Tk thread (garbage the drain's collections skipped because it was frozen: anything frozen at Start that becomes cyclic garbage during the run; the run view kept before Start is no longer one, since Start drops it just before its own collection, which `test_the_kept_views_image_is_freed_on_the_tk_thread` checks) and turns automatic collection back on once per run, whichever way the run ends (the drain, where it runs in a `finally` so an `_onEnded` that raises still clears the worker and gives the controls back; the close poll; a worker that could not start); after Yes in the "Close anyway?" box it stays off and frozen (the process is exiting).
