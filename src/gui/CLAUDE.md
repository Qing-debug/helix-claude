# src/gui: main window and map editor

camelCase package (root CLAUDE.md, "Naming"). `tests/controller/test_map_csv_characterization.py` calls `MapEditor._buildPreviewGraph` on a stand-in `self` to pin the preview order, and `tests/controller/test_map_load_errors.py` calls `MapleGUI._loadMapBrowse` the same way, with `filedialog` and `messagebox` patched, to pin the bad-map message box (decision H16). `tests/controller/test_gui_startup.py` is the one test that builds a real `MapleGUI` on a real, withdrawn Tk root (no mainloop; `after` is replaced by a recorder); it retries the Tk start a few times and skips if Tk still cannot start, because Tk now and then fails to read its own `init.tcl` on the dev PC.

## Traps

- Preview order: `_buildPreviewGraph` (map_editor.py:837) inserts nodes in `map_format.ordered_local_ids` order (map_editor.py:853), the order `write_editor_nodes` (map_csv.py) writes, so the preview's edges match the runtime's after save→load. Change the order only in `ordered_local_ids`.
- The preview builds real `Node`s (map_editor.py:858), so every preview bumps the global `Node.node_id_counter` (`src/controller/CLAUDE.md`); editor loads don't.
- Startup does not wait for the game (decision H18). `_setupGUI` ends with a "Minimap not found yet" label (gui.py:229); `_updateCanvas` (gui.py:441) builds the minimap Canvas in its place on the first frame (`_createMinimapCanvas`, gui.py:424), like `MapEditor._waitForMinimapAndBuildCanvas` does. Until then `minimap_canvas` is None, so any new code that touches it or reads the character from the frame must start with `if not self._minimapReady(): return` (gui.py:232), as the four minimap buttons and `_openMapEditor` do (`_openMapEditor` does nothing else before the first frame: the editor's size checks on load and its node drawing are skipped while its canvas size is unknown, map_editor.py:753, :774, :1019, and nothing redraws the nodes once the canvas appears). Read `minimap_frame` under `minimap_frame_lock` into a local and release the lock before any Tk call or sleep (the old startup loop slept 10 s with the lock held and starved the vision thread).
- The buttons labelled "(delete or move to a separate tab on the GUI)" and "(delete after done testing)" (gui.py:198-215) are test leftovers: `connectCharacterNode` and `deleteNode` are wired with no node argument (controller.py:39-43). Don't build on them.
- The character picker uses `CharacterClass.__subclasses__()` (gui.py:171): direct subclasses only, so a new class must subclass `CharacterClass` directly.
- The GUI reaches past the `Controller` facade into `controller.agent` (gui.py:298, :302, :349, :387); the map editor does too (`buildPathGraphFor`, `characterClass`).
- The character is found by `_findCharacter` (gui.py:240) with route's `CharacterLocator` (decision H20), for "draw blue node on character", "draw orange node on character" and the dev get-path button. It builds the locator from `assets/chr/` on the first press and keeps it; on "miss", "ambiguous" or a bad frame it prints "Character not found on the minimap (<reason>)." in the console, returns None and the button does nothing more (no dot, `node_count` unchanged). Use it, after `_minimapReady()`, for any new button that needs the character's position. It matches outside `minimap_frame_lock`, like `_updateCanvas` draws. The old `getCharacterCoords` is gone; the controller cannot import `src.route` (import-linter contract c), which is why the lookup lives in the GUI. `gui.py` imports `src.route.character` only (no contract forbids it; contract d is the reverse direction): importing more of `src.route` here is a module-boundary change. Not tried on real game frames yet; its limits are in `src/route/character.py`.
- `tests/controller/test_gui_character_buttons.py` covers found, not-found and ambiguous for the three buttons on synthetic frames; it reuses the `make_gui` fixture of `test_gui_startup.py` by import (there is no `conftest.py`).
