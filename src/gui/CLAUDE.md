# src/gui: main window and map editor

camelCase package (root CLAUDE.md, "Naming"). `tests/controller/test_map_csv_characterization.py` calls `MapEditor._buildPreviewGraph` on a stand-in `self` to pin the preview order, and `tests/controller/test_map_load_errors.py` calls `MapleGUI._loadMapBrowse` the same way, with `filedialog` and `messagebox` patched, to pin the bad-map message box (decision H16). `tests/controller/test_gui_startup.py` is the one test that builds a real `MapleGUI` on a real, withdrawn Tk root (no mainloop; `after` is replaced by a recorder); it retries the Tk start a few times and skips if Tk still cannot start, because Tk now and then fails to read its own `init.tcl` on the dev PC. Its `make_gui` fixture hands `make(route_tab_factory=...)` to `MapleGUI` only when given, so a test of the Route tab can pass a fake and the rest get `MapleGUI`'s default. `tests/controller/test_gui_notebook.py` covers the Notebook below; its focus-record test sends Windows' `WM_SETFOCUS` and `WM_KILLFOCUS` to the Setup tab's console in the withdrawn root (in-process: nothing is shown, no key is sent, only the app's own window is addressed) and checks that `focus_get()` follows them, which the app-focus stop (spec 9) relies on. `tests/controller/test_route_tab.py` covers the Route tab: the pure helpers, then the tab on `make_gui`'s root with fakes for the session, free space, the run folder and git (the constructor keywords, below), and the test that `MapleGUI.start` starts the tab's polling; `tests/controller/tk_bans.py` is its flat helper for the source scan of spec 5.12 (below).

## Traps

- The window is a `ttk.Notebook` (gui.py:190) with two tabs, "Setup" and "Route" (`setup_tab`, `route_tab_frame`, gui.py:192-195), 1120x1000 (gui.py:184). All of the old window is in the Setup tab: `_setupScrollableContainer` (gui.py:73) builds the scrolling column inside `setup_tab`; `scrollable_frame` is still the parent of every Setup widget and of the minimap Canvas; the eleven buttons and the class picker are attributes (`draw_blue_node_button` to `get_path_button`, `character_picker`) so the run lock can reach them. `isSetupTabShown()` (gui.py:160) says which tab is selected.
- The Route tab's object comes from `MapleGUI(..., *, route_tab_factory=RouteTab)`: the last step of `_setupGUI` calls `route_tab_factory(route_tab_frame, self)` and keeps the product in `route_tab` (gui.py:283-284). `MapleGUI.start` then calls `route_tab.startPolling()` (gui.py:68-69), the only thing that starts the tab's 100 ms drain (so a test that runs `_setupGUI` alone schedules nothing and runs no git). With the factory `None` the tab is an empty frame and `route_tab` is None (the Notebook tests do this), so code that calls the route tab must work with None; anything that binds to the route tab (the focus bindings of spec 9) goes after that call.
- Run lock: `setRunLocked(locked)` (gui.py:163) disables, or restores, the eleven Setup-tab buttons (draw blue, draw orange, clear console, clear drawn nodes, Load Map, Open Map Editor and the five dev buttons) and the class picker (`readonly` when unlocked), spec 5.1. It leaves the console Text alone, because a disabled `tk.Text` ignores `insert` and `_printToGUIConsole` would go silent, and it leaves the Setup tab's header selectable (waits for Hong: RTF98-1-D1; answer A, the plan's default and what is built, is not Hong's answer yet; answer B would also set `notebook.tab(setup_tab, state=...)` there). A new Setup-tab control must be added to that list: `test_run_lock_disables_exactly_these` fails on a Button or Combobox it does not know.
- Wheel scope: `bind_all('<MouseWheel>')` (gui.py:94) catches every widget of the window, so `_onMouseWheel` (gui.py:98) returns at once unless `isSetupTabShown()`; the Setup tab's scroll canvas (`scroll_canvas`, gui.py:93) never takes wheel events meant for the Route tab.
- Redraw skip: `_updateCanvas` (gui.py:495) keeps its 10 ms loop but builds no picture while the route tab is live (`route_tab.isRunLive()`) and the Setup tab is hidden (gui.py:499-500, :505), so a walk in the same process shares the interpreter with one redraw (spec 5.7); the minimap Canvas is then not created until a frame is drawn. The loop reschedules itself in a `finally` (gui.py:526-528), so a body that raises once does not end it.
- Closing the window: `_setupGUI` sets `WM_DELETE_WINDOW` to `_onClose` (gui.py:175, :185). With no route tab it destroys the root; with one it calls `route_tab.onAppClose(self.gui.destroy)` and the tab decides when the window goes.
- Preview order: `_buildPreviewGraph` (map_editor.py:837) inserts nodes in `map_format.ordered_local_ids` order (map_editor.py:853), the order `write_editor_nodes` (map_csv.py) writes, so the preview's edges match the runtime's after save→load. Change the order only in `ordered_local_ids`.
- The preview builds real `Node`s (map_editor.py:858), so every preview bumps the global `Node.node_id_counter` (`src/controller/CLAUDE.md`); editor loads don't.
- Startup does not wait for the game (decision H18). `_setupGUI` ends with a "Minimap not found yet" label (gui.py:277); `_updateCanvas` (gui.py:495) builds the minimap Canvas in its place on the first frame (`_createMinimapCanvas`, gui.py:478), like `MapEditor._waitForMinimapAndBuildCanvas` does. Until then `minimap_canvas` is None, so any new code that touches it or reads the character from the frame must start with `if not self._minimapReady(): return` (gui.py:286), as the four minimap buttons and `_openMapEditor` do (`_openMapEditor` does nothing else before the first frame: the editor's size checks on load and its node drawing are skipped while its canvas size is unknown, map_editor.py:753, :774, :1019, and nothing redraws the nodes once the canvas appears). Read `minimap_frame` under `minimap_frame_lock` into a local and release the lock before any Tk call or sleep (the old startup loop slept 10 s with the lock held and starved the vision thread).
- The Route tab is `src/gui/route_tab.py` (`RouteTab`, route_tab.py:210; C5 of `docs/superpowers/plans/2026-10-31-route-tab.md`, spec 5.2-5.5). It is `src.gui`'s one door to the run driver: it imports `src.route.session` (which reaches `src.input`) and `src.route_view`, and nothing else in `src.gui` may import `src.input` (import-linter contract "gui reaches input only through the run driver", `allow_indirect_imports = true` so the chain through `session` passes). `src.gui` and `src.main` are not sources of "route_view is a leaf" for the same reason (spec 5.9); the view itself still imports nothing from the app. It imports `MapleGUI` under `TYPE_CHECKING` only, because `gui.py` imports `RouteTab`. The module also holds the pure helpers (`validateSettings`, `classKey`, `endedText`, `countdownText`, route_tab.py:69 and on), which touch no Tk. The constructor keywords (`make_session`, `make_thread`, `run_root`, `disk_free`, `new_out`, `git_head`, `frame_checks`, ...) are the seams tests and the sim tool use; tests pass fakes and patch no module name. The constructor calls no `after`, no git and no disk probe. Readiness: `drainEvents` (route_tab.py:392, every 100 ms, rescheduling itself through the root's `after` in a `finally`) refreshes Start and the status line only with no worker and an idle state (`not_ready`, `ready`, `ended`; `_refreshReadiness`, :369), and writes the status line only when its inputs or text changed, so a Start refusal or an Ended text stays until a field, the map, the class or the minimap state changes (plan choice 8). It reads the minimap as `minimap_canvas is not None` and prints nothing: `MapleGUI._minimapReady()` prints into the Setup console, so only Start (`startRun`, :515) calls it. Start runs spec 5.4's checks in order and, with all passed, builds the session through `make_session`, locks the Setup tab (`setRunLocked`) and its own controls (only Stop stays usable) and starts the run's worker, a daemon thread named `route-run` built by `make_thread`, whose body `_work` (:558) runs `session.run()` and prints anything that escapes it (so `threading.excepthook` never sees it). While `worker` is set, or the window waits to close, Start does nothing (one worker at most). Threads: the worker never touches Tk; the session's `on_event` is the tab's `queue.Queue.put`, and `drainEvents` reads the queue on the Tk thread (`_showEvent`, :425: 5.2's texts, a `warning` appended in any state, `ended` → `_onEnded` then `endedText`), then runs the watchdog: a worker found dead is read as ended only after one more drain finds no `ended` (spec 5.5), and a dead worker gives every control back. `_onRunning` and `_onEnded` are the hooks RT-8b fills (no-op and False here). Stop (`stopRun`, :567) calls `session.stop("button")`, which returns at once. `isRunLive` is the state test the redraw skip needs. Closing the window (`onAppClose`, :469, spec 5.5 "Closing the app mid-run"): with no worker the hosted view goes, then the window, at once; with one it calls `session.stop("window_close")`, shows "Stopping: releasing keys..." and polls every 100 ms (`_pollClose`, :487) until the worker has ended, or for `CLOSE_WAIT_S` (10 s, read from the `clock` keyword), after which it prints one console line and destroys anyway (the worker is a daemon). A second press while it waits keeps the one poll loop. The teardown order is the live view's `stop()`, the view's `destroy()`, then the window's (`_closeWindow`, :501), because `RouteViewWindow.destroy()` raises TclError once its host is gone; the window's `destroy` runs in a `finally`, so a view that raises cannot keep the window open. Threads on each end: on Stop and on a session error the worker ends when `run()` returns (the drain then clears it); on app close it gets up to 10 s, then dies with the process. Spec 5.12 (rules 2-3) in the tab: no dialog, no Toplevel, no Combobox, no `wm` style or icon call (`overrideredirect`, `resizable`, `transient`, `attributes`, `iconbitmap`, `iconphoto`) and no focus call (`focus`, `focus_set`, `focus_force`, `lift`, `tkraise`, `grab_set`), in or out of a run (the game is usually open either way). Two tests hold it: the source scan `focus_problems` (`tests/controller/tk_bans.py`) over `route_tab.py`, and a run from Start to the close with those calls patched on `tk.Misc`, `tk.Wm`, `tk.Toplevel` and the three dialog modules. `gui.py` is not scanned (its class picker is a Combobox and Load Map opens dialogs, both greyed out during a run). `frame_checks=False` skips the minimap and character checks (and the minimap part of readiness) for the sim tool only.
- The buttons labelled "(delete or move to a separate tab on the GUI)" and "(delete after done testing)" (gui.py:246-263) are test leftovers: `connectCharacterNode` and `deleteNode` are wired with no node argument (controller.py:39-43). Don't build on them.
- The character picker uses `CharacterClass.__subclasses__()` (gui.py:219): direct subclasses only, so a new class must subclass `CharacterClass` directly.
- The GUI reaches past the `Controller` facade into `controller.agent` (gui.py:352, :356, :403, :441); the map editor does too (`buildPathGraphFor`, `characterClass`).
- The character is found by `_findCharacter` (gui.py:294) with route's `CharacterLocator` (decision H20), for "draw blue node on character", "draw orange node on character" and the dev get-path button. It builds the locator from `assets/chr/` on the first press and keeps it; on "miss", "ambiguous" or a bad frame it prints "Character not found on the minimap (<reason>)." in the console, returns None and the button does nothing more (no dot, `node_count` unchanged). Use it, after `_minimapReady()`, for any new button that needs the character's position. It matches outside `minimap_frame_lock`, like `_updateCanvas` draws. The old `getCharacterCoords` is gone; the controller cannot import `src.route` (import-linter contract c), which is why the lookup lives in the GUI. `gui.py` imports `src.route.character` and, for the Route tab, `src.gui.route_tab`; no contract forbids the first (contract d is the reverse direction). Not tried on real game frames yet; its limits are in `src/route/character.py`.
- `tests/controller/test_gui_character_buttons.py` covers found, not-found and ambiguous for the three buttons on synthetic frames; it reuses the `make_gui` fixture of `test_gui_startup.py` by import (there is no `conftest.py`).
