camelCase package (root CLAUDE.md, "Naming"). `tests/controller/test_map_csv_characterization.py` calls `MapEditor._buildPreviewGraph` on a stand-in `self` to pin the preview order, and `tests/controller/test_map_load_errors.py` calls `MapleGUI._loadMapBrowse` the same way, with `filedialog` and `messagebox` patched, to pin the bad-map message box (decision H16). `tests/controller/test_gui_startup.py` is the one test that builds a real `MapleGUI` on a real, withdrawn Tk root (no mainloop; `after` is replaced by a recorder); it retries the Tk start a few times and skips if Tk still cannot start, because Tk now and then fails to read its own `init.tcl` on the dev PC. ## Traps

- The window is a `ttk.Notebook` (gui.py:190) with two tabs, "Setup" and "Route" (`setup_tab`, `route_tab_frame`, gui.py:192-195), 1120x1000 (gui.py:184). All of the old window is in the Setup tab: `_setupScrollableContainer` (gui.py:73) builds the scrolling column inside `setup_tab`; `scrollable_frame` is still the parent of every Setup widget and of the minimap Canvas; the eleven buttons and the class picker are attributes (`draw_blue_node_button` to `get_path_button`, `character_picker`) so the run lock can reach them. `isSetupTabShown()` (gui.py:160) says which tab is selected.
- The Route tab's object comes from `MapleGUI(..., *, route_tab_factory=RouteTab)`: the last step of `_setupGUI` calls `route_tab_factory(route_tab_frame, self)` and keeps the product in `route_tab` (gui.py:284-285). `MapleGUI.start` then calls `route_tab.startPolling()` (gui.py:68-69), the only thing that starts the tab's 100 ms drain and fills its saved-run list (so a test that runs `_setupGUI` alone schedules nothing, runs no git and lists no `data/route`). With the factory `None` the tab is an empty frame and `route_tab` is None (the Notebook tests do this), so code that calls the route tab must work with None. The focus bindings of spec 9 (gui.py:286-288) come after that call and only with a tab (pre-flight m6; with none nothing is bound): `<FocusIn>` and `<FocusOut>` on the root with `add="+"`, each scheduling one `after_idle(route_tab.rereadFocus)` (the Route tab bullet below). Every widget of the main window has the root's tag in its bindtags, so they see a focus event on any of them; the map editor is a Toplevel with its own tag chain and is not covered (Start refuses while it is open). In the withdrawn test root a generated focus event reaches the bindings only when generated on the root itself, not on a child widget.
- Run lock: `setRunLocked(locked)` (gui.py:163) disables, or restores, the eleven Setup-tab buttons (draw blue, draw orange, clear console, clear drawn nodes, Load Map, Open Map Editor and the five dev buttons) and the class picker (`readonly` when unlocked), spec 5.1. It leaves the console Text alone, because a disabled `tk.Text` ignores `insert` and `_printToGUIConsole` would go silent, and it leaves the Setup tab's header selectable (waits for Hong: RTF98-1-D1; answer A, the plan's default and what is built, is not Hong's answer yet; answer B would also set `notebook.tab(setup_tab, state=...)` there). A new Setup-tab control must be added to that list: `test_run_lock_disables_exactly_these` fails on a Button or Combobox it does not know.
- Wheel scope: `bind_all('<MouseWheel>')` (gui.py:94) catches every widget of the window, so `_onMouseWheel` (gui.py:98) returns at once unless `isSetupTabShown()`; the Setup tab's scroll canvas (`scroll_canvas`, gui.py:93) never takes wheel events meant for the Route tab.
- Redraw skip: `_updateCanvas` (gui.py:499) keeps its 10 ms loop but builds no picture while the route tab is live (`route_tab.isRunLive()`) and the Setup tab is hidden (gui.py:503-504, :509), so a walk in the same process shares the interpreter with one redraw (spec 5.7); the minimap Canvas is then not created until a frame is drawn. The loop reschedules itself in a `finally` (gui.py:530-532), so a body that raises once does not end it.
- Closing the window: `_setupGUI` sets `WM_DELETE_WINDOW` to `_onClose` (gui.py:175, :185). With no route tab it destroys the root; with one it calls `route_tab.onAppClose(self.gui.destroy)` and the tab decides when the window goes.
- Preview order: `_buildPreviewGraph` (map_editor.py:837) inserts nodes in `map_format.ordered_local_ids` order (map_editor.py:853), the order `write_editor_nodes` (map_csv.py) writes, so the preview's edges match the runtime's after save→load. Change the order only in `ordered_local_ids`.
- The preview builds real `Node`s (map_editor.py:858), so every preview bumps the global `Node.node_id_counter` (`src/controller/CLAUDE.md`); editor loads don't.
- Startup does not wait for the game (decision H18). `_setupGUI` ends with a "Minimap not found yet" label (gui.py:277); `_updateCanvas` (gui.py:499) builds the minimap Canvas in its place on the first frame (`_createMinimapCanvas`, gui.py:482), like `MapEditor._waitForMinimapAndBuildCanvas` does. Until then `minimap_canvas` is None, so any new code that touches it or reads the character from the frame must start with `if not self._minimapReady(): return` (gui.py:290), as the four minimap buttons and `_openMapEditor` do (`_openMapEditor` does nothing else before the first frame: the editor's size checks on load and its node drawing are skipped while its canvas size is unknown, map_editor.py:753, :774, :1019, and nothing redraws the nodes once the canvas appears). Read `minimap_frame` under `minimap_frame_lock` into a local and release the lock before any Tk call or sleep (the old startup loop slept 10 s with the lock held and starved the vision thread).
- The Route tab is `src/gui/route_tab.py` (`RouteTab`, route_tab.py:314; C5 of `docs/superpowers/plans/2026-10-31-route-tab.md`, spec 5.2-5.5). It is `src.gui`'s one door to the run driver: it imports `src.route.session` (which reaches `src.input`) and `src.route_view`, and nothing else in `src.gui` may import `src.input` (import-linter contract "gui reaches input only through the run driver", `allow_indirect_imports = true` so the chain through `session` passes). `src.gui` and `src.main` are not sources of "route_view is a leaf" for the same reason (spec 5.9); the view itself still imports nothing from the app. It imports `MapleGUI` under `TYPE_CHECKING` only, because `gui.py` imports `RouteTab`. The module also holds the pure helpers (`validateSettings`, `classKey`, `endedText`, `countdownText`, route_tab.py:86 and on), which touch no Tk. The constructor keywords (`make_session`, `make_thread`, `run_root`, `disk_free`, `new_out`, `git_head`, `make_minimap`, `frame_checks`, ...) are the seams tests and the sim tool use; tests pass fakes and patch no module name. The constructor calls no `after`, no git and no disk probe. Readiness: `drainEvents` (route_tab.py:517, every 100 ms, rescheduling itself through the root's `after` in a `finally`) refreshes Start and the status line only with no worker, no close waiting and an idle state (`not_ready`, `ready`, `ended`; `_refreshReadiness`, :493), and writes the status line only when its inputs or text changed, so a Start refusal or an Ended text stays until a field, the map, the class or the minimap state changes (plan choice 8). It reads the minimap as `minimap_canvas is not None` and prints nothing: `MapleGUI._minimapReady()` prints into the Setup console, so only Start (`startRun`, :788) calls it. Start runs spec 5.4's checks in order and, with all passed, builds the session through `make_session`, locks the Setup tab (`setRunLocked`) and its own controls (only Stop stays usable) and starts the run's worker, a daemon thread named `route-run` built by `make_thread`, whose body `_work` (:852) runs `session.run()` and puts the traceback of anything that escapes it on the tab's line queue (so `threading.excepthook` never sees it, and it reaches the console box, not the terminal); a worker that cannot be built or started ends the run at once with the watchdog's text and every control back, and the error goes on to Tk's callback handler. While `worker` is set, or the window waits to close, Start does nothing (one worker at most). The console box (spec 5.5 "Where the details go", H71; orchestrator ruling RDO110-D3 = A, orch 110, which Hong may still overturn): every line a run in the app prints goes to the Setup tab's console, none to the terminal. `_toConsole(text, error)` (:581) is the tab's one writer (`_printToGUIConsole`, trailing newlines stripped; `error` marks where a colour goes later, none now). Lines from other threads (the worker's `traceback.format_exc()`, the session's `log`, which `startRun` passes to `make_session` as the fifth argument, the tab's `_postLine`) wait on a tab-private `queue.SimpleQueue` that `drainEvents` empties (`_drainLines`) before the run events, the watchdog's second drain included, and `_drainQueue` empties again just before it shows an `ended`; the live view's `report` and the idle minimap's run on the Tk thread and call `_errorToConsole` at once. The close's give-up line (`CLOSE_GAVE_UP_TEXT`) is still a `print` (RT-8a-D1 is open); it is the one line of an app run that still goes to the terminal. The lines printed below the session (runtime's `run_cleanup` and stop control, the walker, the step log) reach the box too: the session hands each of them its `_error_line`, its `log` with the error flag set, through a `log` keyword (RT-8c piece 4b, ruling orch 111; `src/route/CLAUDE.md`, the `RunSession` bullet), and `test_lines_below_the_session_reach_the_console_box` pins it in the tab. Threads: the worker never touches Tk; the session's `on_event` is the tab's `queue.Queue.put`, and `drainEvents` reads the queue on the Tk thread (`_showEvent`, :619: 5.2's texts, a `warning` appended in any state, `ended` → `_onEnded` then `endedText`, and while Stopping a late `status` or `countdown` changes nothing while a `running` still reaches `_onRunning`), then runs the watchdog: a worker found dead is read as ended only after one more drain finds no `ended` (spec 5.5), and a dead worker gives every control back. The app-focus stop (spec 9, H64): `app_has_keyboard` is a `threading.Event` that only the Tk thread sets and clears, in `rereadFocus` (:892). It reads Tk's own focus record (`gui.focus_get()`, no Windows call): one of our widgets sets the flag, None clears it, and a KeyError (a widget Tk made itself, such as a Combobox drop-down's list, which tkinter's `nametowidget` does not know) counts as ours. On a rise (clear, then set) in `countdown` or `running` it calls `session.stop("app_focus")` after setting the flag and changes neither the state nor the status line, so a Stop press that follows still sends `button` and the session, which keeps the first trigger, ends with the click text (H73); before Start, while Stopping and after the end a rise only sets the flag. A rise that finds the tab still connecting first shows the events queued so far (`_drainQueue`) and tests the state again, stopping the run if it is now in the countdown or walking, even if showing them raised (RT-9-R m1): a drain step that blocks the Tk thread for the whole countdown schedules the next step only once it returns, so Tcl runs the click's idle re-read first (idle callbacks run only when no event is queued, and a timer is queued only once due), while the worker's `countdown` and `running` still wait on the queue; `test_focus_rise_with_the_runs_events_still_queued_stops` reproduces that order. With nothing queued a rise while connecting only sets the flag. The root's focus bindings schedule it (the `route_tab_factory` trap above) and Start calls it once, before Connecting. Closing the window (`onAppClose`, :743, spec 5.5 "Closing the app mid-run"): with no worker the hosted view goes, then the window, at once; with one it calls `session.stop("window_close")`, shows "Stopping: releasing keys..." and polls every 100 ms (`_pollClose`, :761) until the worker has ended, or for `CLOSE_WAIT_S` (10 s, read from the `clock` keyword), after which it prints one console line and destroys anyway (the worker is a daemon). A second press while it waits keeps the one poll loop. While it waits the drain still reads the queue and clears a dead worker, but writes no status line and gives no control back (`_say`, :575), so the Stopping text and the lock hold until the window goes. The teardown order is the live view's `stop()`, the view's `destroy()`, then the window's (`_closeWindow`, :777), because `RouteViewWindow.destroy()` raises TclError once its host is gone; the window's `destroy` runs in a `finally`, so a view that raises cannot keep the window open. Threads on each end: on Stop and on a session error the worker ends when `run()` returns (the drain then clears it); on app close it gets up to 10 s, then dies with the process. Garbage collection during a run (RT-8a I1, ruling RT-8a-review-D1 A): Python's cycle collector runs on whichever thread allocates past its threshold, and on the worker it could free a Tk object whose `__del__` calls Tcl, which waits for the Tk thread with no timeout and can deadlock it on a lock both take (the event queue's). So Start calls `gc.collect()`, `gc.disable()` and `gc.freeze()` on the Tk thread just before `worker.start()`; while the worker lives the drain calls `gc.collect()` every `GC_EVERY_POLLS` (10) steps, about once a second, and because what existed at Start is frozen, that collection walks only what the run has made since (ruling orch 108; measured with the app's modules imported, Python 3.14.0: a full collection of the app's ~123 500 objects takes about 23 ms, one just after the freeze under 0.1 ms, one with 50 000 objects made since about 1.5 ms). `_clearWorker` (:562) unfreezes, collects once on the Tk thread (garbage the drain's collections skipped because it was frozen: anything frozen at Start that becomes cyclic garbage during the run; the run view kept before Start is no longer one, since Start drops it just before its own collection, which `test_the_kept_views_image_is_freed_on_the_tk_thread` checks) and turns automatic collection back on once per run, whichever way the run ends (the drain, where it runs in a `finally` so an `_onEnded` that raises still clears the worker and gives the controls back; the close poll; a worker that could not start); after the 10 s close give-up it stays off and frozen (the process is exiting). Nothing the worker runs (`src/route`, `src/input`) may call `gc.collect()`. `tests/controller/test_route_tab.py` unfreezes and turns it back on after every test (autouse `_collector_back_on`), because a fake worker left alive leaves it off and frozen. Saved runs (spec 5.11, plan choice 13; RT-10): `savedRuns(run_root)` (:186) lists the folders directly under the run root that hold `steps.jsonl` or `legs.jsonl`, newest first by name, each labelled `<local start time>  <map file stem>  <N> laps` from `session.json`'s `start_utc` and `map` and the line count of `laps.jsonl`, with `?` for what cannot be read; a missing run root is an empty list. The first fill is in `startPolling()`, never in the constructor: every `make_gui` test builds a tab, and a fill there would list the dev PC's real `data/route` and sum its frame files. Refresh (`refreshSavedRuns`, :928) fills again. Each fill writes every row ending "size ..." and starts a new `saved-run-sizes` daemon thread, always a real `threading.Thread` (never `make_thread`, which builds only the run's worker: a test's inline thread would sum on the Tk thread), kept in `size_thread` so a test can `join()` it before `drainEvents()`. Its body (`_sumSizes`, :946) touches no Tk: it puts `(generation, folder, bytes)` from `folderSize` (`os.scandir`, recursive, OSError skipped) on a second `queue.SimpleQueue` (its `put` runs in C and holds no lock the drain waits on), which `drainEvents` empties after the run's events (`_drainSizes`, :956), writing `formatSize`'s `<n> MB` or `<x.y> GB` into the row. Each fill is a new generation: an older generation's results are dropped, and an older thread stops before its next folder. Nothing else stops it: on close it is a daemon that dies with the process, and since it never touches Tk the close needs nothing from it. A disabled Listbox ignores insert, delete and selection changes (Tk), and a run disables the list while sums may still arrive, so every row edit goes through `_editableList` (:976), which enables the list for the edit and sets its state back.
