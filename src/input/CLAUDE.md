# src/input: input over Bluetooth

Presses keys in the game through the ESP32-S3. Spec: `docs/superpowers/specs/2026-10-21-p1a-input-over-bluetooth-design.md`; plan: `docs/superpowers/plans/2026-10-21-p1a-input.md`. The `InputLayer` API, the `Link` protocol, the reaction-time rule and the safety rules are in the root CLAUDE.md.

## Seams

`protocol` (pure, bytes) → `link` (`BleLink`) → `input_layer` (`InputLayer`, what other packages call) → `harness/` (measurement tools; nothing in `src/route` or the controller imports them).
- `protocol.py` (pure): wire protocol v1, binary, little-endian: `ver`, then `op` or `kind`, then `seq` u16 (assigned by the PC, echoed in the replies). Commands `PLAY`, `RELEASE_ALL` and `PING` are writes with response to the command characteristic. A `PLAY` is at most 16 steps of (`delta` in 100 µs units, key mask), each step changes exactly one key, the last mask is 0, and the total is at most 10 s; the PC and the board both validate it. Notifications `ACCEPTED`, `DONE`, `REJECTED` and `PONG` come back on the notify characteristic. `PONG` `flags`: bit0 bonded, bit1 encrypted, bit2 authenticated, bit3 HID input report subscribed. `Key` is the mask: four arrows, `E`, `ALT` (left Alt, sent as a HID modifier) and `SPACE`, the only keys the bot sends. Named codes `DoneStatus`, `RejectReason` and `play_len(n)` (`play_len(16) == 53`); `Done.status` and `Rejected.reason` stay raw `int`, so an unknown code still decodes.
- `timing.py` (pure): `TimingModel` draws every value from one seeded `numpy` `Generator`. `MODEL` holds the parameters and is the single source for the sampling and for the KS reference CDFs.
- `actions.py` (pure): `tap`, `walk`, `teleport`, `drop`, `jump`, `jump_off` and `sequence` build a `Plan`, the steps plus the timing `Sample`s drawn for them.
- `link.py`: `BleLink` runs bleak on a daemon event-loop thread behind a blocking API (`connect`, `play`, `release_all`, `ping`, `faults`, `take_pongs`, `close`). `connect()` succeeds only once a `PONG` shows bonded, encrypted, subscribed and `mtu` ≥ 56. The device name and UUIDs live here (`DEVICE_NAME`, `CMD_UUID`, `NOTIFY_UUID`).
- `input_layer.py`: `Link` is at input_layer.py:31-37; `_clock` / `_sleep` (input_layer.py:23-24) are module globals that tests patch.

## Traps

- MapleStory question (H60). `soak.maple_check` (soak.py) reads the answer through `soak._read_answer`, which calls `input(soak.PROMPT)`; only `y` passes, and a closed input is a `Failure`. Each tool asks exactly once per run, before the listener, the link or any key, and never again: `soak` through `soak._check_processes` in `run_soak`, `session_starts` through `session_starts._check_processes` in `run_starts`, `probe` at step 1 in `run_probes` (`soak.maple_check()` through the module); `probe._check_processes(writer, answer)` only writes that one answer into each probe's `session.json` and never asks. The tests patch `soak._read_answer` by name (test_probe, test_session_starts, test_soak, test_soak_v2_faults; `test_guard_targets.py` adds its own): if the function moves, those patches stop reaching the question and a test would block on real input. `tests/input/test_guard_targets.py` fails if a patched name stops being defined in its module. Never move or rename `maple_check`, `_read_answer` or `_check_processes` (the last name is historical: it no longer lists processes). The key-timing check is the one caller that hands `soak` an answer instead of letting it ask (next bullet).
- `soak.py` is a library in practice: `probe` and `session_starts` use its private names `soak._SoakSink` (probe.py:1004, :1096; session_starts.py:164, :220), `soak._stamp_perf_ns` (probe.py:985), `soak.check_focus` (session_starts.py:138) and its constants (probe.py:52-53). Renaming one means editing all three files. The key-timing check (`tools/key_timing_check.py`, last bullet below) is a fourth user, of `soak._new_link` (soak.py:671) and `soak._start_sink` (soak.py:674), and the only caller that hands `soak` an answer: `run_check` asks the question once with `soak.maple_check()` (key_timing_check.py:404) and passes the text to each arm's `soak.run_soak(cfg, soak._new_link(), soak._start_sink, answered=text)` (:425). With `answered` set, `run_soak` (soak.py:594-595) hands it to `_check_processes(writer, answered)` (:553, :606), which asks nothing, records the text as `process_check` and lets the run go on only if the text is `soak.ANSWERED_Y` (soak.py:502, what `maple_check` returns for a `y`); any other text refuses the run as an `n` would. `main` never passes `answered`, so a soak from the command line still asks, and the question is still asked once per run (of the check, for all its arms). `test_only_the_key_timing_check_hands_soak_an_answer` (tests/input/test_key_timing_check.py:796) fails if any other file under `src/` or `tools/` passes `answered`, names `ANSWERED_Y` or uses the accepted text.
- winrt chain: `faults.py` imports `winrt.windows.devices.radios` at module level (faults.py:44-45); `soak` imports `faults` (soak.py:57), and `probe` and `session_starts` import `soak`. None of the four imports without winrt, so their tests do not collect off Windows.
- `Key` and the wire format reach past this package: `src/route/planner.py:18`, `src/route/sim/{link,run,world}.py` and `harness/soak.py:61` import `Key`, and the firmware mirrors the format. A format change edits `firmware/test/vectors.json` first (`tests/input/test_protocol.py` and `firmware/test/test_protocol.cpp` both read it); `tests/input/test_firmware_constants.py` fails if a constant here and in `protocol.h` / `Helix_BLE.ino` disagree. Host-test commands: `firmware/CLAUDE.md`.
- Test fakes: `tests/input/input_fakes.py` (`FakeLink`, `FakeClock`, `pong()`, `report()`), imported as `from input_fakes import ...`. basedpyright type-checks that file, so `_satisfies_link` (input_fakes.py:68-70) fails the check if `FakeLink` stops matching `Link`. The other fakes (test_input_layer `Clock`, test_session_starts `FakeLink`, test_soak_v2_faults `Link`, and those in test_soak and test_probe) differ on purpose and stay local.
- Codes: `PA-*` and `A-*` are `docs/decisions.md` headings; `C1`-`C5`, `H1`-`H4` and `V1`-`V3` are ids in the plan.

## Harness tools (`src/input/harness/`)

Each tool runs from the repo root as `python -m src.input.harness.<tool>`. The ones that send keys (`probe`, `soak`, `session_starts`) need the board, a real Bluetooth link and the "Helix input test sink" window (opened by the listener, where the board's keys land), and every run directory goes under `data/` (gitignored: `soak/`, `probe/`, `starts/`). Never run them with MapleStory open (root CLAUDE.md, "Safety rules"). An agent may run them, and may flash or reset the board, without asking Hong when the work needs it, MapleStory is not running (the tools ask; see the root CLAUDE.md H15 bullet for how an agent answers) and nobody is using the PC: check the time since the last keyboard or mouse input, or ask Hong, because a person's typing lands in the focused window and fails `analyze`'s Delivery check (H15 in `docs/decisions.md`; the sink window, the real link and the `data/` keylog rule still hold).
- `listener --out DIR [--seconds 20] [--no-block]`: a low-level keyboard hook that logs to `DIR/keys.jsonl`, plus the sink window. It records every key event on the machine, for all virtual-key codes, not only the bot keys. By default it also blocks the seven bot keys system-wide after recording them; `--no-block` passes them through.
- `probe [--probes LIST] [--run NAME] [--out DIR] [--seed N] [--cli PATH] [--link-debug] [--run-sheet]`: fixed measurement scripts through `InputLayer` and the listener, one run directory per probe. `--run-sheet` prints the live run sheet and runs nothing, `--link-debug` logs each probe's link records at DEBUG, and `--cli` is the `arduino-cli` used for the board-port check.
- `soak --commands N [--min-hours H] [--seed S] [--out DIR] [--short] [--faults reset_board=5,bluetooth_off_on=5]`: a seeded mix of commands through `InputLayer`, optionally with injected board resets and Bluetooth off/on. It waits up to 120 s for you to click the sink, aborts on `FOCUS_LOST` (the sink lost the foreground), and refuses a `--commands` that gives fewer than `realism.KS_MIN_N` (1000) samples of any type `realism` KS-tests (`realism.KS_TYPES`: hold, gap, chord offset, reaction) unless `--short` (a dry run or fault soak, which `realism` does not judge). `soak` imports both from `realism`, so the check cannot drift from the judge (H21); walk and release-lag samples are drawn and logged but not required.
- `session_starts [--out DIR] [--seed N]`: 20 session starts (8 plain, 6 after a board reset, 6 after a Bluetooth off/on), each followed by one tap of `E` that the listener must see.
- `analyze RUN_DIR [--starts session_starts.jsonl]` and `realism RUN_DIR`: offline checks on a soak run directory (delivery, latency, faults, stuck keys and connection; then timing realism by a KS test per type against `MODEL`, and delivered timing). Both exit non-zero on a FAIL.
- `faults` (the injectors `soak` uses) and `g4_check` (a one-off check that resets the board) are helpers.
- `tools/key_timing_check.py [--out data/keytiming/<name>] [--commands 2000] [--seed 1] [--at X,Y]` (in `tools/`, not a harness module; its docstring has the arms, the decision rule and the exit codes, and is out of date on two points that this bullet has right: whether the search arms' capture rate is judged, and a Ctrl+C between arms): the check that a capture running flat out does not make the keys late (H104). It sends keys through `soak`, so the root CLAUDE.md Safety rules hold for it; it is Hong-gated and outside the standing permission above, so an agent never runs it. It starts `tools/capture_load_window.py` as a process of its own, a test window that changes every frame so that the capture runs flat out; the window keeps redrawing after one picture fails. Under `--out` it writes one soak folder per arm, `<k>-pause<P>ms/`, with `arm.json` (the pause, pictures a second, walker reads, `window_alive` (the test window's process was still running at the arm's end), `minimap_lost` (the capture lost the test window's minimap during the arm), the Delivery verdict, the listener's state and the residual's n, p50 and p99), and `result.json` (the rules, every finished arm, and `result`, the pause in ms or "inconclusive", with `reason`). An arm whose test window had closed or whose minimap was lost, or (a search arm only) whose pictures a second fell below the first 20 ms arm's, reads "lost its load" and makes the result "inconclusive": it measured some other load. A soak that does not end normally, or a Ctrl+C, stops the check with exit 1 and the arms so far kept: `result.json` has `"stopped"` and no `result`, as `"arm <k>: <exit code>"` when an arm's soak ended abnormally or Ctrl+C came in it or in its analysis (130 for Ctrl+C), and as `"between arms, after arm <k>: 130"` or `"before arm 1: 130"` for a Ctrl+C outside any soak; a Ctrl+C at the question writes nothing. Its tests are `tests/input/test_key_timing_check.py`.
