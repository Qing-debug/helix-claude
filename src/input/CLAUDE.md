# src/input: input over Bluetooth

Presses keys in the game through the ESP32-S3. Spec: `docs/superpowers/specs/2026-10-21-p1a-input-over-bluetooth-design.md`; plan: `docs/superpowers/plans/2026-10-21-p1a-input.md`. The `InputLayer` API, the `Link` protocol, the reaction-time rule and the safety rules are in the root CLAUDE.md.

## Seams

`protocol` (pure, bytes) → `link` (`BleLink`) → `input_layer` (`InputLayer`, what other packages call) → `harness/` (measurement tools; nothing in `src/route` or the controller imports them).
- `protocol.py` (pure): wire protocol v1, binary, little-endian: `ver`, then `op` or `kind`, then `seq` u16 (assigned by the PC, echoed in the replies). Commands `PLAY`, `RELEASE_ALL` and `PING` are writes with response to the command characteristic. A `PLAY` is at most 16 steps of (`delta` in 100 µs units, key mask), each step changes exactly one key, the last mask is 0, and the total is at most 10 s; the PC and the board both validate it. Notifications `ACCEPTED`, `DONE`, `REJECTED` and `PONG` come back on the notify characteristic. `PONG` `flags`: bit0 bonded, bit1 encrypted, bit2 authenticated, bit3 HID input report subscribed. `Key` is the mask: four arrows, `E`, `ALT` (left Alt, sent as a HID modifier) and `SPACE`, the only keys the bot sends. Named codes `DoneStatus`, `RejectReason` and `play_len(n)` (`play_len(16) == 53`); `Done.status` and `Rejected.reason` stay raw `int`, so an unknown code still decodes.
- `timing.py` (pure): `TimingModel` draws every value from one seeded `numpy` `Generator`. `MODEL` holds the parameters and is the single source for the sampling and for the KS reference CDFs.
- `actions.py` (pure): `tap`, `walk`, `teleport`, `drop`, `jump` and `sequence` build a `Plan`, the steps plus the timing `Sample`s drawn for them.
- `link.py`: `BleLink` runs bleak on a daemon event-loop thread behind a blocking API (`connect`, `play`, `release_all`, `ping`, `faults`, `take_pongs`, `close`). `connect()` succeeds only once a `PONG` shows bonded, encrypted, subscribed and `mtu` ≥ 56. The device name and UUIDs live here (`DEVICE_NAME`, `CMD_UUID`, `NOTIFY_UUID`).
- `input_layer.py`: `Link` is at input_layer.py:31-37; `_clock` / `_sleep` (input_layer.py:23-24) are module globals that tests patch.

## Traps

- MapleStory guard. `soak.maple_check` (soak.py:518) calls `soak._process_names` (soak.py:506). `probe._check_processes` (probe.py:1002) and `session_starts._check_processes` (session_starts.py:154) call `soak.maple_check()` through the module. 13 patch sites set `soak._process_names` by name (test_probe 4, test_session_starts 3, test_soak 5, test_soak_v2_faults 1; `test_guard_targets.py` adds 5 more): if the function moves, those patches stop reaching the guard and nothing says so. `tests/input/test_guard_targets.py` fails if a patched name stops being defined in its module. Never move or rename `maple_check`, `_process_names` or `_check_processes`.
- `soak.py` is a library in practice: `probe` and `session_starts` use its private names `soak._SoakSink` (probe.py:1009, :1103; session_starts.py:160, :222), `soak._stamp_perf_ns` (probe.py:988), `soak.check_focus` (session_starts.py:134) and its constants (probe.py:51). Renaming one means editing all three files.
- winrt chain: `faults.py` imports `winrt.windows.devices.radios` at module level (faults.py:44-45); `soak` imports `faults` (soak.py:58), and `probe` and `session_starts` import `soak`. None of the four imports without winrt, so their tests do not collect off Windows.
- `Key` and the wire format reach past this package: `src/route/planner.py:16`, `src/route/sim/{link,run,world}.py` and `harness/soak.py:61` import `Key`, and the firmware mirrors the format. A format change edits `firmware/test/vectors.json` first (`tests/input/test_protocol.py` and `firmware/test/test_protocol.cpp` both read it); `tests/input/test_firmware_constants.py` fails if a constant here and in `protocol.h` / `Helix_BLE.ino` disagree. Host-test commands: `firmware/CLAUDE.md`.
- Test fakes: `tests/input/input_fakes.py` (`FakeLink`, `FakeClock`, `pong()`, `report()`), imported as `from input_fakes import ...`. basedpyright type-checks that file, so `_satisfies_link` (input_fakes.py:68-70) fails the check if `FakeLink` stops matching `Link`. The other fakes (test_input_layer `Clock`, test_session_starts `FakeLink`, test_soak_v2_faults `Link`, and those in test_soak and test_probe) differ on purpose and stay local.
- Codes: `PA-*` and `A-*` are `docs/decisions.md` headings; `C1`-`C5`, `H1`-`H4` and `V1`-`V3` are ids in the plan.

## Harness tools (`src/input/harness/`)

Each tool runs from the repo root as `python -m src.input.harness.<tool>`. The ones that send keys (`probe`, `soak`, `session_starts`) need the board, a real Bluetooth link and the "Helix input test sink" window (opened by the listener, where the board's keys land), and every run directory goes under `data/` (gitignored: `soak/`, `probe/`, `starts/`). Never run them with MapleStory open (root CLAUDE.md, "Safety rules").
- `listener --out DIR [--seconds 20] [--no-block]`: a low-level keyboard hook that logs to `DIR/keys.jsonl`, plus the sink window. It records every key event on the machine, for all virtual-key codes, not only the bot keys. By default it also blocks the seven bot keys system-wide after recording them; `--no-block` passes them through.
- `probe [--probes LIST] [--run NAME] [--out DIR] [--seed N] [--cli PATH] [--link-debug] [--run-sheet]`: fixed measurement scripts through `InputLayer` and the listener, one run directory per probe. `--run-sheet` prints the live run sheet and runs nothing, `--link-debug` logs each probe's link records at DEBUG, and `--cli` is the `arduino-cli` used for the board-port check.
- `soak --commands N [--min-hours H] [--seed S] [--out DIR] [--short] [--faults reset_board=5,bluetooth_off_on=5]`: a seeded mix of commands through `InputLayer`, optionally with injected board resets and Bluetooth off/on. It waits up to 120 s for you to click the sink, aborts on `FOCUS_LOST` (the sink lost the foreground), and refuses a `--commands` that gives fewer than 1000 samples per KS type unless `--short` (a dry run or fault soak, which `realism` does not judge).
- `session_starts [--out DIR] [--seed N]`: 20 session starts (8 plain, 6 after a board reset, 6 after a Bluetooth off/on), each followed by one tap of `E` that the listener must see.
- `analyze RUN_DIR [--starts session_starts.jsonl]` and `realism RUN_DIR`: offline checks on a soak run directory (delivery, latency, faults, stuck keys and connection; then timing realism by a KS test per type against `MODEL`, and delivered timing). Both exit non-zero on a FAIL.
- `faults` (the injectors `soak` uses) and `g4_check` (a one-off check that resets the board) are helpers.
