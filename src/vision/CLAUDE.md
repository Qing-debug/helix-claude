# src/vision: minimap capture

How it works is in the root CLAUDE.md ("Vision", "Threads and shared state"). `tests/vision/test_frame_wait.py` drives `frame_wait.py` and `cameraGrab` with a fake camera (Windows only); no other test runs this package, and two read `vision.py` as text (the last bullet under Traps).

## Traps

- Don't rename or restructure `vision.py` or `vision_helper_lib.py`: Feature C starts from Helix's rune work including its uncommitted changes to both files (`docs/superpowers/specs/2026-10-21-p1c-runes-design.md:28`), and a restructure here turns that port into a hand merge.
- `bettercam` is imported at module scope (vision.py:1), so importing `src.vision.vision` needs Windows and bettercam. `src/route` may import it only inside a function (`src/route/harness/record_minimap.py:163`); `tests/route/test_import_rules.py` and import-linter contract e enforce that.
- When the corner match fails, the loop goes straight back (`continue`, vision.py:60-62) to another full-monitor grab and match, with no sleep (the grab itself still waits for a new image, next bullet). Inside the minimap loop, the grab's wait and `time.sleep(THREAD_SLEEP_DURATION_S)` (vision.py:82, a 20 ms floor between frames (H80) that binds only above about 45 frames a second) pace it.
- Every grab waits inside Windows for a new desktop image (H77, Hong's QA116-1 answer): `cameraGrab` (vision_helper_lib.py) calls `frame_wait.grab_new_frame` (`src/vision/frame_wait.py`), which asks Windows' desktop duplication with `AcquireNextFrame(NEW_FRAME_TIMEOUT_MS = 100)` where bettercam's own `grab` passes 0, so it never spins on failed grabs: it returns at the next new image, or None after 100 ms on a screen where nothing changed, and `cameraGrab` asks again. An update that moved only the mouse pointer gives None. `cameraGrab` imports `frame_wait` inside the function because `frame_wait` loads bettercam and `src/route/harness/detection_check.py` imports `vision_helper_lib` without it (`test_41` in `tests/route/test_detection_check.py` checks bettercam stays out). Tests patch `frame_wait.grab_new_frame` and `frame_wait._query_texture` (the one call on a real COM pointer).
- `frame_wait.py` is a copy of bettercam 1.0.0's `BetterCam.grab`/`_grab` (`bettercam/bettercam.py:70-94`) and reads its private parts (`_duplicator`, `_device`, `_stagesurf`, `_processor`, `_on_output_change`, `_validate_region`). bettercam is pinned (`requirements.txt`, `bettercam==1.0.0`), and `test_bettercam_is_pinned_to_the_version_the_helper_copies` fails if the installed version changes or one of those names leaves bettercam's source. An upgrade means re-reading bettercam's grab path and updating the copy, not only the pin.
- `vision_helper_lib.py:3` imports `enum.Enum` unused; ruff's F401 is ignored for that file in `pyproject.toml` on purpose, so the file stays as Helix has it until the port.
- The capture loop opens no OpenCV window (H67, spec 5.12-5): the window's key wait became a 10 ms `FRAME_DELAY_MS` sleep (RT-11), which the grab's wait for a new image replaced (H77); the loop's one sleep is the floor at vision.py:82. Two tests in `tests/test_anti_cheat_names.py` read `vision.py` as text: the name scan (spec 5.12-4 and 5.12-5) fails if one of 5.12-5's three OpenCV window and key-wait names comes back, and `test_capture_loop_keeps_its_pause` fails if the floor line goes or `FRAME_DELAY_MS` comes back.
